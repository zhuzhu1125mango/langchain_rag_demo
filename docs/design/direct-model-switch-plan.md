# 直答模型切换与 A/B 验证执行方案

> 关联文档：[chat-latency-and-model-config.md](chat-latency-and-model-config.md) §11.5（背景分析）

> 日期：2026-10-03

## 0. 目标

将直答+辅助任务模型从 `qwen3:4b-instruct-2507-q4_K_M`（2.5GB，仅 69% 上 GPU，decode 27~33 tok/s）切换为可全量驻留 GPU 的小模型，实现：

1. 默认路径（`deep_thinking=off`）decode 速度提升至 ≥45 tok/s（目标 1.5~2 倍）
2. 直答模型 100% GPU 常驻，消除权重 CPU 卸载
3. 模型换载（思考⇄非思考切换）恢复时间缩短（1.4GB vs 2.5GB 重载）

不改变：主模型 `qwen3:4b`（`deep_thinking=on` 专用）、embedding `bge-m3`（动了须重建 Milvus 索引）、reranker 配置。

## 2. 执行阶段

### 阶段一：基线采集（切换前，现任 4B 直答模型）

**1.1 准备测试问题集**（固定 8 题，后续每轮复用同一组）：

| # | 类型 | 说明 |
|---|---|---|
| Q1~Q3 | 通用问答（无 KB） | 闲聊、常识、稍长的解释类问题 |
| Q4~Q6 | 知识库问答 | 需引用标注 [1][2]、遵循禁前缀等模板约束 |
| Q7~Q8 | 深度思考 | `deep_thinking=on`，验证 qwen3:4b 路径不受影响 |

**1.2 KB 测试数据**：若默认 KB 无文档（`document_count=0`），先导入 2~3 篇测试文档到测试知识库；已有则跳过。

**1.3 逐题采集基线并记录**：
- 首 token 延迟、完整回答耗时（前端或浏览器开发者工具的网络事件时间轴）
- `ollama ps`：记录 GPU/CPU 分层比（当前实测 31%/69%）
- `request_traces` 表：核对 generate 段耗时与输出速度（字段以实际表结构为准）
- Q4~Q6 人工记录：引用标注是否正确、是否违反禁前缀

**1.4 记录换载耗时**：触发一次 `deep_thinking=on` → off 切换，记录模型重载时间（浏览器请求耗时 - ollama 加载）。

### 阶段二：切换到候选 A（qwen3:1.7b）

```powershell
Copy-Item .env.prod .env.prod.bak-20261003   # 备份，回滚开关
```

`.env.prod` 修改（仅两行）：

```ini
# 修改前
OLLAMA_DIRECT_MODEL_NAME=qwen3:4b-instruct-2507-q4_K_M
FAST_LLM_MODEL_NAME=qwen3:4b

# 修改后
OLLAMA_DIRECT_MODEL_NAME=qwen3:1.7b
FAST_LLM_MODEL_NAME=qwen3:1.7b
```

保持不变：`OLLAMA_MODEL_NAME=qwen3:4b`、`EMBEDDING_MODEL_NAME=bge-m3`、`OLLAMA_SUPPORTS_THINKING=true`（主模型仍是思考模型）。

重启后端，确认启动日志中模型校验（`/api/tags`）无报错。

### 阶段三：A/B 第一轮验证（qwen3:1.7b）

**冒烟顺序**（每步通过再进下一步）：

1. **思考链泄漏专项**：Q1~Q3 以 `deep_thinking=off` 提问，检查回答无 `<think>` 块、无"让我思考"类前缀 → 任何泄漏即判不合格
2. **KB 引用质量**：Q4~Q6 检查 [1][2] 引用格式正确、无禁前缀违规、内容忠实于检索片段
3. **深度思考回归**：Q7~Q8 开 `deep_thinking=on`，确认思考链正常产出（此步应触发 qwen3:4b 加载）
4. **换载恢复**：紧接着切回 off 提问，记录 1.7b 重载耗时（预期优于基线）
5. **辅助任务抽查**：新会话标题生成正常；换几种意图（闲聊/KB/联网）确认路由结果合理
6. **GPU 常驻确认**：`ollama ps` 显示候选 A 为 `100% GPU`（无 CPU 百分比）

**量化记录**：与阶段一相同口径（首 token、总耗时、tok/s、换载耗时）。

**合格判定**（须同时满足）：
- 性能：decode ≥ 基线 1.5 倍或 ≥45 tok/s；`ollama ps` 无 CPU 层
- 质量：Q4~Q6 引用/禁前缀违规合计 ≤1 处；Q1~Q3 零思考链泄漏；中文表达无明显退化

合格 → 跳到阶段五；不合格 → 阶段四。

### 阶段四：A/B 第二轮（qwen2.5:3b-instruct）

重复阶段二~三流程（`.env.prod` 两行改为 `qwen2.5:3b-instruct`）。

差异点：
- 天生非思考模型，第 1 步思考链泄漏风险为零，重点转向指令遵循
- 预期 decode 略慢于 1.7b（40~55 vs 55~75 tok/s），关注是否仍达标（≥45 tok/s）

产出三栏对比表：基线 / 候选 A / 候选 B（性能 + 质量两维）。

**定稿决策规则**：
- 两者均合格 → 取速度更快者
- 仅一者合格 → 取合格者
- 均不合格 → 回滚（阶段六），问题升级为"3B/1.7B 均不满足质量要求"，另行评估

### 阶段五：定稿与清理

1. `.env.prod` 定稿为最终候选
2. 删除旧直答模型：`ollama rm qwen3:4b-instruct-2507-q4_K_M`
3. 可选：删除落选候选（`ollama rm qwen3:1.7b` 或 `qwen2.5:3b-instruct`；磁盘充裕可保留观察一段时间）
4. 文档同步：
   - `README.md` 模型表（非思考模型默认值）
   - `docs/architecture.md` 开发栈模型清单
   - `chat-latency-and-model-config.md` 追加"§12 实测结果"（tok/s、GPU 分层、换载耗时、质量结论）

### 阶段六：回滚预案（贯穿全程）

- **旧模型删除前**（阶段二~五期间任意时刻）：恢复备份并重启即回滚


- **阶段三、四均已执行**：候选 A 已达标，但为得到方案要求的对比结论与"取速度更快者"的判据，仍完成候选 B。
- **未执行阶段五的删除动作**：旧模型本就已不存在；落选候选按 §2 阶段五第 3 条"磁盘充裕可保留观察"保留。
- **阶段六未触发**。

### 6.2 对比（`request_traces.stages` 实测；模型相关）

| 维度 | 基线 `qwen3:4b-instruct-2507-q4_K_M`（已删） | 候选 A `qwen3:1.7b` | 候选 B `qwen2.5:3b-instruct` |
|---|---|---|---|
| 工作集 / GPU 分层 | 3.9 GB，40%/60% CPU/GPU | 2.0 GB，**100% GPU** | 2.3 GB，**100% GPU** |
| decode（trace 换算） | 27.6 tok/s | 90~107 tok/s（**含隐藏思考 token**） | 55~71 tok/s（无思考） |
| 短答 generate（墙钟） | 3.1~8.8 s | Q2 2.3s / Q4 2.0s / Q6 5.0s | **Q2 1.3s / Q4 0.9s / Q6 1.6s** |
| 首个 off 请求 generate | 冷启偏慢 | 9.3 s（异常） | **1.5 s** |
| 4b→小模型换载恢复（generate 含重载） | — | ~6.1 s（含约 4 s 重载） | ~6.1 s 量级 |
| 辅助/直答 GPU 常驻 | 否 | 是 | 是 |

> 说明：候选 A 的 token 数含 Ollama 隐藏思考链（同一 KB 短答 A 记 179 tokens、B 仅 26），故其 tok/s 数字偏高、墙钟反而更慢。

### 6.3 质量结论

- **候选 A**：Q1~Q3（off）零思考链泄漏（`/api/chat` 复核：思考被 Ollama 分离到 `thinking` 字段，正文干净）；Q4/Q6 及补测题均正确引用 `[1]`；中文正常。
- **候选 B**：零泄漏；Q4 引用正确，**Q6 稳定漏 `[1]`（2/2 复现）**，达方案门槛上限（违规合计 ≤1）；中文正常。
- 两者均通过方案合格门（性能 ≥45 tok/s、无思考链泄漏、违规 ≤1）。
- **已定稿候选 B（2026-10-03）**：按方案"均合格取速度更快者"规则取墙钟最快者——B（0.9~1.6s vs A 的 2.0~5.0s）。A 的 tok/s 优势（90~107）系隐藏思考 token 抬高的假象（同题 179 vs 26 token），且思考模型占用非思考槽位架构不契合。Q6 漏 `[1]` 转入提示词工程单独修复，不阻塞定稿。

### 6.4 执行中发现的无关既有问题（不在本方案范围）

1. **天气城市提取器误判**：`_extract_city_name`（[_weather_impl.py](../../backend/src/services/tools/plugins/_weather_impl.py#L44-L90)）在问题含"温度/气温/…天气"时会把前置短语当作城市名，导致 Q5（"最大吞吐量和工作温度范围"）被路由到 `weather_query` 并返回"无法找到相关信息"。**与模型无关**，基线同样受影响；建议单独修（`_DIAGNOSTIC_RE` 已排除诊断类，但"温度"仍误命中）。
2. **KB 检索耗时以 CrossEncoder 重排为主**（2026-10-03 实测，KB 8 块）：`kb_retrieval` 稳态 **2.8~3.1 s**，重启后首查 **8.8 s**（Milvus 首次加载）。拆解：bge-m3 query embedding（CPU，`num_gpu=0`）仅 **~45 ms**；瓶颈是 CPU 上的 `bge-reranker-v2-m3` CrossEncoder 打分——实测**按 token 线性增长**（≈10 ms/token：20 token≈1.0 s、37 token≈0.7 s、616 token≈6.9 s），5 个候选合计 **~3.5 s**，且**与语料规模无关**（固定送重排候选数）。
   **已实施优化（2026-10-08）**：`KB_HYBRID_RERANK_TOP_K` 5→3（`.env.prod` / `.env.dev`）。复测同题 10 条独立样本：稳态 `kb_retrieval` **1.3~1.8 s**（中位 ≈1.6 s），**较 5 对基线省 ≈1.4 s（≈47%）**，与预测一致；KB 查询端到端总耗时从 4.3~4.5 s 降至 **2.0~2.7 s**。质量核对：10/10 均带 `[1]` 引用、答案正确。注意该参数的实际语义：`rerank_n = max(TOP_K, KB_HYBRID_RERANK_TOP_K)`，两值同为 3 时重排只对 RRF 前 3 名打分——质量代价是"RRF 排 4~5 名但语义更相关的候选"不再有机会进前 3（此前重排可提拔）；`KB_RERANK_MIN_SCORE=0` 下不做过滤。若后续发现检索质量退化，回退只需改回 5。
   **冷启动数据口径**：重启后首查（5 对时 8.8 s / 3 对时 6.3 s）含一次性成本——Milvus 集合首次加载与 BM25 词表载入（约 4~5 s，与 `KB_HYBRID_RERANK_TOP_K` **无关**）+ 重排首推理预热，因此**首查耗时不可用于评估该参数收益**，对比一律以稳态为准（-1.4 s）。另 2026-10-08 复测时宿主机为刚冷启动，前 3 个样本（6.3→4.6→3.8 s）呈 CPU 频率/页缓存爬坡的递减趋势，约第 4 个样本起进入稳态——单机评估此类延迟应跳过重启后前 3~4 次查询再采样。
3. **测量方法学**：用 httpx 测 SSE 延迟会因 gzip/读取缓冲虚高约 21 s（curl 实测首字节仅 0.23 s）；应以 `request_traces.stages` 或 curl（不带 gzip）为准。

### 6.7 引用标注提示词修复（2026-10-03）

针对 §6.3 候选 B 的 Q6 稳定漏 `[1]`，在 KB 回答模板 `KB_ANSWER_TEMPLATE`（[pipeline/state.py](../../backend/src/services/pipeline/state.py#L44-L45)）强化引用要求：

- 规则 3 由"关键事实必须标注来源编号"扩写为"**分点、分步骤或并列多条事实时，每一条都要各自标注**，不得整篇无编号、或只在末尾统一标注一次"；
- 结尾生成指令补"（每个事实性陈述均须标注来源编号）"。

验证（重建后端镜像后，逐次清语义缓存取独立样本）：

- 候选 B：Q6 步骤类 **3/3 均带 `[1]`**（修复前 0/3）；Q4 单事实仍带 `[1]`。
- 主模型 `qwen3:4b`（`deep_thinking=on`）：Q4 返回"…保修期为36个月[1]。"，无过度标注回归。

副作用：B 的步骤回答在强引用要求下偶尔把 `[1]` 紧跟在"…步骤如下："之后（位置略显生硬），不影响可读性与溯源。
