# 端到端验证：真实文档能答成什么样（2026-11-03）

> 此前所有评测都在**合成语料**上做：78 篇制度/产品文档是我编的，90 道题也是我编的。
> 检索指标、通道对比、显著性检验都在这上面算。系统**从未端到端回答过一个真问题**。
>
> 这次拿 4 份真实的项目文档灌进生产知识库，问 10 个我知道答案的问题，
> 人眼判断对错。结论：**能用，但只在细节型问题上；概览型问题会给出自信的错答案。**

## 1. 怎么测的

| 项 | 内容 |
|---|---|
| 语料 | 真实项目文档 4 份：`deployment.md`（57KB）、`architecture.md`（19KB）、`backup-restore.md`（16KB）、`monitoring.md`（15KB） |
| 切分 | 生产 `CHUNK_SIZE=512 / OVERLAP=64`，共 **502 个 chunk**（296 / 71 / 72 / 63） |
| 链路 | 生产 `/api/chat/stream`，`search_mode=simple`，`top_k=3`，`bge-m3` + `bge-reranker-base` |
| 问题 | 10 个，覆盖部署、迁移、监控、备份、架构、运维，答案我全部知道 |
| 判据 | 人眼比对答案与文档原文。不看指标，只看"这话对不对、有没有出处" |

不复用评测脚本：那套脚本只算 hit/mrr，算不出"答案里有没有编"。

## 2. 结果：4 好 / 2 偏 / 4 差

| # | 问题 | 耗时 | 结果 |
|---|---|---|---|
| 1 | 生产环境怎么部署？ | 0.2s | ❌ 秒回，只说"请参考文档 [1][2]"，没给任何步骤 |
| 2 | 数据库迁移怎么执行？ | 4.4s | ⚠️ 答成了 `downgrade` 流程（问的是迁移怎么执行） |
| 3 | 监控哪些指标、有哪些告警？ | 1.5s | ❌ 只列 3 个指标，**12 条告警一条没提**，却说"并设置相应的告警" |
| 4 | 备份怎么恢复？恢复后确认什么？ | 7.2s | ✅ 完整分步 + 命令 + 4 项确认 |
| 5 | 系统由哪些部分组成，请求怎么流转？ | 4.4s | ❌ 纯泛泛而谈，末尾自曝"基于训练数据" |
| 6 | 怎么查看 PostgreSQL 指标？ | 1.9s | ⚠️ 答成 target 配置，没说怎么看指标 |
| 7 | 优雅停机怎么做？为什么需要？ | 6.5s | ❌ 纯编造，自曝"基于训练数据" |
| 8 | 为什么要给 NLTK 语料单独放进镜像？ | 7.6s | ✅ 根因 + 具体做法 |
| 9 | ScrapeTargetDown 是什么意思？ | 1.6s | ✅ 准确简洁 |
| 10 | 改完告警规则怎么生效？ | 2.7s | ✅ 准确，还补充了 promtool 校验 |

平均 4.0 秒（0.2–7.6s）。

### 规律：问题越"大"越差

- **细节型**（`ScrapeTargetDown`、NLTK 原因、promtool 命令）：答案集中在文档某一段，top-3 拼得出来 → 答得好。
- **概览型**（系统架构、部署步骤、优雅停机）：答案分散在多个章节，top-3 拼不全 → 模型自己编。

而"编"的代价是：`architecture.md` 有完整架构图与请求流转说明，`deployment.md` 有完整部署章节，
**它们都进了库、也被检索到了，但相关度不够（见 §3），最终没进上下文**。

用户拿到的是一个通顺、专业、看起来像真的错误答案。

## 3. 两个缺陷（已修）

### C11：trace 从不记录检索结果

`TraceCollector.set_kb_results()` / `set_search_results()` **定义了却全项目无人调用**，
93 条 trace 的 `kb_results`、`search_results` 全是 null。

后果不是"少个字段"，而是无法区分两种修法完全相反的故障：

| 现象 | 真实原因 | 该改哪里 |
|---|---|---|
| 检索结果为空 | 没检索到 | 召回：索引、切分、embedding |
| 检索结果为空 | 检索到但被判不相关 | 重排阈值、prompt、上下文拼接 |

两者在 trace 里看到的都是"空"。

**修复**：`kb_stage` 在相关性判定**之前**记录候选（判定为不相关时会清空 `docs`，
在清空后写就丢掉最该复盘的那批）；`finalize_stages` 统一补写 web 来源。

**修完立刻拿到决定性证据**：

```
整个系统由哪些部分组成 → 3 条候选，rerank_score = 0.077 / 0.011 / 0.006
优雅停机是怎么做的   → 3 条候选，rerank_score = 0.009 / 0.000 / 0.000
阈值 KB_RELEVANCE_SCORE_THRESHOLD = 0.3
```

**两题都远低于阈值**——也就是说，相关性判定本身是对的，`docs` 也确实被清空了。

### C12（记录，未修）：删库后语义缓存索引残留

巡检报 `dangling_cache_index`：索引 SET 里指向已删除的 scope，索引键靠 25h TTL 自然过期。
影响极小（一条 SET 键），但会让巡检长期报差异、失去"exit 0 = 健康"的意义。
修法：`invalidate_kb` 删完条目后同步 `SREM` 索引成员，索引空则删键。

## 4. 真正的缺陷：把"知识库里没有"翻译成"请你编一个"

C11 的证据说明检索判定是对的。那答案为什么还是编的？看生成阶段的提示词选择：

```python
# generation_stages.py，context 为空时
prompt = LLM_DIRECT_TEMPLATE.format(...)
```

而 `LLM_DIRECT_TEMPLATE` 的第一句是：

```
你是一个智能助手。本次联网搜索未能返回有效结果。
请基于你已有的知识回答用户问题：
- 非时效性问题：正常回答。
```

**这句模板是给"联网搜索失败"写的，却被"知识库检索未命中"共用。**
等于系统已经算出"知识库里没有"，却把这个结论翻译成"请你用自己的知识答一个"。

（`KB_ANSWER_TEMPLATE`——context 非空时用的那个——反而明确写着"如果参考信息中没有答案，
直接说明无法找到相关信息"。也就是说：**有上下文时要求拒答，没上下文时要求编造**。）

### 修复

新增 `KB_MISS_TEMPLATE`，用 `state.kb_retrieval_attempted` 区分两种"没有上下文"：

| 场景 | 标记 | 模板 | 对用户的含义 |
|---|---|---|---|
| 检索过知识库但没命中 | `True` | `KB_MISS_TEMPLATE` | 必须明说"知识库中没有找到" |
| 压根没检索（纯聊天） | `False` | `LLM_DIRECT_TEMPLATE` | 正常基于模型知识回答 |

`KB_MISS_TEMPLATE` 的关键要求：

1. **第一句必须明确说明**：在你指定的知识库中没有找到相关内容
2. **禁止编造**，**不要标注 [1][2]**（本次没有任何可信来源）
3. 若用通用知识补充，必须先标明"以下为模型自身知识，未经知识库验证"
4. 依赖具体文档的问题（内部流程、参数、部署步骤）只声明未找到，不猜测

`answer_type` 新增 `kb_miss`，Prometheus 可直接统计拒答量。

### 修复后（同一批问题重跑）

```
修复前：整个系统通常由前端用户界面、后端处理逻辑、数据库和数据存储、网络通信等部分组成……
       （末尾）以上信息基于训练数据，可能不具备实时性

修复后：在你指定的知识库中没有找到与这个问题相关的内容。
       以下为模型自身知识，未经知识库验证：整个系统通常由前端界面、后端处理逻辑……
```

用户第一眼就知道这不是知识库答案，而不是读到末尾才发现。

正常路径未受影响（换措辞重测，避开语义缓存）：

- 「数据库备份的恢复流程是什么？」→ 分步 + 命令 + 引用 [2] ✅
- 「NLTK 语料为什么不能放在挂载卷里？」→ 根因准确 ✅

## 5. 仍然没解决

**概览型问题为什么检索不到？** 两题 rerank_score 是 0.077 和 0.009，
而 `architecture.md` 里明明有答案。可能原因：

- `bge-reranker-base` 对"整个系统由哪些部分组成"这种宽泛问句不敏感；
- 答案分散在多个 chunk，没有任何单块与该问题高度匹配；
- 提问用语与文档用语差异大（"组成"vs"架构总览"）。

修法方向（未验证）：概览型问题给 5–8 段而不是 3 段；或按标题路径做章节级召回。
**但现在至少它不再假装知道。**

## 6. 复现

```bash
# 上传真实文档到临时知识库，跑 10 个问题并记录答案
E2E_TOKEN=<jwt> E2E_KB=<kb_id> E2E_OUT=out.json \
  python scripts/e2e_verify_chat.py

# 事后复盘：每题检索到了什么、分数多少
docker exec postgres-prod psql -U prod_user -d app_prod -tAc "
select left(question,22),
       jsonb_array_length(kb_results::jsonb),
       (select string_agg(round((e->'metadata'->>'rerank_score')::numeric,3)::text, ',')
        from jsonb_array_elements(kb_results::jsonb) e)
from request_traces where kb_results is not null order by created_at desc limit 10;"
```

## 7. 边界

- **10 个问题定不了总体水平**：只够发现失败模式，不足以给"准确率"。要数字，需要 100+ 题并人工标注。
- **语料是项目文档**：结构规整、有明确标题层级，比真实企业文档（扫描件、Word 混排、表格）干净。
- **只测了 `simple` 模式**：`deep_thinking`、Agent 模式、多查询改写都没走。
- **答案对错是人眼判断**：没有客观评分标准，"4 好"是我的判断，不同人可能有分歧。
- **语义缓存会干扰复测**：同一措辞第二次问会命中缓存、跳过生成。验证修复效果必须换措辞。
