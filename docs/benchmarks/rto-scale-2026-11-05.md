# 真实规模 RTO：把「几秒恢复」从 500 chunk 的样本推到万级

> 此前所有恢复数字（PG 6s / MinIO 4s / Milvus 37s）都是在**生产那份 4 文档 532 chunk**
> 的数据量上量的，文档里自己写着「不能外推」。这一页补上规模：PG 做到 **915MB / 60 万行**、
> Milvus **2 万向量**、MinIO **1000 对象 / 195MB**，并且给出**两个规模点**而不是一个点，
> 这样才有斜率可言。
>
> 复现：`scripts/scale_rto_drill.sh`（`MODE=pg|milvus|minio|all`）。全部在**隔离实例**上跑，
> 生产容器与生产卷只被读，不被写。

## 1. 一页结论

| 组件 | 数据量 | 备份 | 恢复（RTO） | 校验 |
|---|---|---|---|---|
| PostgreSQL | **915MB / 3 万文档 / 60 万 trace** | 46s → 61MB | **22s** | 行数逐表一致、alembic `d5e6f7a8b9c0` |
| PostgreSQL | 312MB / 1 万文档 / 20 万 trace | 17s → 21MB | 6s | 同上 |
| Milvus | **2 万向量（1024 维 dense + sparse）** | 2~3s → 71MiB | **29~33s** | 条数 20000、双索引类型、稀疏字段在 |
| MinIO | **1000 对象 / 195MB** | 5s → 196MB | **18s** | 对象数 1000、内容哈希集合一致 |

**一句话**：PG 的恢复是 **40~50MB/s 量级**（约每 GB 20s），Milvus 只有 **3MB/s 量级**
（恢复被索引重建拖住），MinIO 单流 **约 22MB/s**。所以真到百万向量，**Milvus 才是那个
决定深夜能不能睡着的东西**，不是数据库。

## 2. PostgreSQL：两个点，斜率 2.7~3.7 倍

| | 库大小 | 备份产物 | 备份耗时 | 恢复耗时 | 恢复吞吐 |
|---|---|---|---|---|---|
| 1×（1 万文档 / 20 万 trace / 1 万会话） | 312MB | 21MB | 17s | **6s** | 52MB/s |
| 3×（3 万文档 / 60 万 trace / 3 万会话） | 915MB | 61MB | 46s | **22s** | 42MB/s |
| 倍数 | 2.93× | 2.90× | 2.71× | **3.67×** | 0.80× |

数据量涨 2.93 倍，恢复涨 3.67 倍——**略超线性**（索引重建与 `ANALYZE` 的固定开销在
这个量级还没被摊薄）。按 42MB/s 保守外推：

| 假设库大小 | 备份耗时 | 产物 | 恢复 |
|---|---|---|---|
| 1GB | 约 0.9 min | 约 68MB | 约 0.4 min |
| 5GB | 约 4.3 min | 约 340MB | 约 2.0 min |
| 20GB | 约 17 min | 约 1.4GB | 约 8 min |

备份侧读盘速度两个点都是 **18~20MB/s**，很稳定——瓶颈不在 CPU（gzip 单核已经够），
而在「读表 + 压缩 + 写盘」这条串行链上。要更快只能并行 `pg_dump -j`，但 `-Fc` 的
目录格式与现在 `restore.sh` 按魔数分派的逻辑不兼容，属于改造而不是调参。

## 3. Milvus：恢复被索引重建拖成 3MB/s

| 指标 | 值 |
|---|---|
| 集合 | 20000 条 / 1024 维 dense + sparse（模拟 BM25 词权重） |
| 灌数据 + 建索引 | 4.8s + 7.1s（**不计入 RTO**，这是源实例的准备成本） |
| 备份 | 2~3s，71MiB / 9 objects |
| 目标实例启动（etcd + MinIO + Milvus） | 6~10s |
| 恢复（`restore --rebuild_index`） | 23s |
| **RTO** | **29~33s**（两次跑：29s / 33s，抖动来自冷启动） |
| 校验 | `entities=20000`、`vec:HNSW` + `sparse:SPARSE_INVERTED_INDEX` 双索引都在 |

71MiB / 23s ≈ **3.1MB/s**，比 PG 慢一个数量级：`--rebuild_index` 是恢复了数据之后再
把 HNSW 图重新构建一遍，耗时随条数近似线性、但常数很大。外推：

| 向量数 | 备份体积 | 恢复（按 3.1MB/s） |
|---|---|---|
| 10 万 | 约 0.4GiB | 约 2 min |
| 100 万 | 约 3.5GiB | **约 19 min** |

**这是全套里最该被写进预案的一条**：如果哪天语料涨到百万 chunk，Milvus 恢复会从
半分钟变成二十分钟，而且是单线程重建索引。缓解手段（按代价排序）：先把
`documents` 的索引换成 IVF_FLAT（重建快、召回略降），或者接受更长的 RTO 并把
「Milvus 可重建」写进预案——向量是 chunk 的派生物，**最坏情况下可以从 PG + MinIO
重算**，这一点比数据库宽容得多。

## 4. MinIO：单流 22MB/s，可并行

| 指标 | 值 |
|---|---|
| 对象 | 1000 个 × 200KB = 195MB |
| 备份（`mc mirror` 到宿主机） | 5s（39MB/s） |
| 目标实例启动 | 1s |
| 回灌 | 9s（22MB/s） |
| **RTO** | **18s** |
| 校验 | 对象数 1000、1000 个 sha256 排序后再哈希一致（`178fd28d661524e3`） |

回灌比备份慢一倍，因为 `mc mirror` 往新实例写是逐对象 PUT，小对象场景下每次
请求的固定开销占比高。100GB 原件按此速度约 **79 min**；但 `mc mirror` 支持并发，
实际可以通过多进程把这条压下来——这是三个组件里**唯一容易水平加速**的。

## 5. 这些数字不能说明什么

按之前的规矩，每条都写清楚边界，避免被当成 SLA：

1. **合成数据比真实数据好压。** 三个规模点的 gzip 压缩比都稳定在 **15:1**（312MB→21MB、915MB→61MB），
   因为合成文本是重复模板。真实文档（PDF 抽取、表格、代码）大概 3~5:1，**同样的库会产出 3~4 倍大的备份**，
   备份与恢复都要相应变慢。表里的「按 42MB/s 外推」用的是**恢复吞吐**，与压缩比无关，这一项还算稳。
2. **单机同盘，没有网络。** 备份写、恢复读都在同一块 NVMe 上，Docker 卷也在本地。
   真实灾备是跨机甚至跨对象存储，网络会成为新瓶颈；这里量到的是**下限**。
3. **RTO 的口径是「数据回到可服务状态」**，不含后端冷启动（加载 embedding 模型要
   **27~48s**，见 `guide/backup-restore.md` §7.3）、不含流量切换与 DNS。
   把后端算进去，PG 场景的真实可用时间应该是 **22s + 30s 上下**。
4. **每组只有一两个样本。** Milvus 跑了两次得 29s / 33s，冷启动抖动就有 4s；
   PG 的 3× 点只跑了一次。要拿趋势得靠重复跑，这一页给的是量级不是精测。
5. **不是并发压测。** 恢复期间没有业务流量，也没有和备份任务叠跑。
   顺带划清一条界线：本页的 RTO **不等于**「企业级三门槛」里的容量实测
   （那一条要的是 **X 并发下的 P95 与成功率**），别拿这里的秒数去顶。

## 6. 复现

```bash
MODE=pg     ./scripts/scale_rto_drill.sh      # 3 万文档 / 60 万 trace（默认 1 万 / 20 万）
MODE=milvus ./scripts/scale_rto_drill.sh      # 2 万向量（1024 维 dense + sparse）
MODE=minio  ./scripts/scale_rto_drill.sh      # 1000 对象 × 200KB
MODE=all    ./scripts/scale_rto_drill.sh      # 三件串起来

# 换规模（脚本里的默认值都能覆盖）
PG_DOCS=30000 PG_TRACES=600000 MODE=pg ./scripts/scale_rto_drill.sh
MILVUS_ROWS=100000 MODE=milvus ./scripts/scale_rto_drill.sh
```

结果落在 `backups/scale-rto/results-<模式>.md`，日志同名 `.log`。演练用的实例与卷
全部以 `dscale_` 开头，结束自动清理；生产容器与生产卷只读。

⚠️ 宿主机上的**种子与备份副本**不会自动删（删上千个文件会撞批量删除策略，脚本刻意不做）：
一轮 `MODE=all` 大约在 `backups/scale-rto/` 留 **0.9GB**，确认不用留档后手动清理即可。

机器：i5-12500H（16 逻辑核）/ 16GB / SK Hynix NVMe，Docker Desktop，全部实例与卷在同一块盘上。

## 7. 这一轮脚本踩到的坑（都不是演练结论，但都会让结论假通过）

| 现象 | 真因 | 处理 |
|---|---|---|
| 死在「本地生成对象」，无任何报错 | 删 1000 个文件的 `rm -rf` 撞批量删除策略，脚本静默退出 | 种子与暂存目录都不再先清空（同名覆盖写），备份目录带时间戳 |
| MinIO 哈希「看起来一致」 | minio 镜像里没有 `sha256sum`，容器内算出来是空输入，两侧都退化成 `e3b0c442…` | 哈希一律回宿主机算，并断言结果不等于空串哈希 |
| 目标 MinIO `bucket does not exist` 后静默退出 | `mc mirror` 先于 `mc mb` 执行 | 先建 bucket 再 mirror，失败显式报错 |
| 同一批结果互相覆盖 | 三个模式共用一个 `results.md`，后跑的把它清了 | 按模式分文件 `results-<mode>.md` |
| 只打印「源 X 个 / 目标 X 个」不判定 | 没有通过/不通过判据，人眼看着「一致」就过了 | 加对象数与哈希集合的硬判定，不一致返回非零 |
