# 概览型问题丢在哪一级：检索逐级探针（2026-11-03）

> 端到端验证（[e2e-verification-2026-11-03.md](../e2e-verification-2026-11-03.md)）的结论是
> 「问题越大越差」，当时给的解释是 **rerank 对宽泛问句不敏感**。
> 这个解释**没有证据**：生产 trace 只存了 rerank 之后的 top-3（`KB_HYBRID_RERANK_TOP_K=3`），
> 我们看到的 0.077 / 0.009 是「3 条候选里最好的」，不是「20 条候选里最好的」。
>
> 两种故障的修法完全相反——池里没有（改召回）vs 池里有但被挤出（改融合/窗口）。
> 这份报告把三级摊开，逐级定位。

## 1. 怎么测的

| 项 | 内容 |
|---|---|
| 语料 | 与端到端验证同一批 4 份真实文档，**生产切分器**（`ChunkingFactory`，`CHUNK_SIZE=512 / OVERLAP=64`）→ **502 个 chunk**（architecture 71 / deployment 296 / backup-restore 72 / monitoring 63） |
| 通道 | sparse = BM25（同生产 jieba 分析器）；dense = Ollama `bge-m3`；融合 = RRF（k=60，等权）；重排 = `bge-reranker-base`（`max_length=256`，CPU） |
| 题目 | 10 道，5 概览 + 5 细节，题干沿用端到端验证 |
| 指标 | **事实点覆盖率**：把答案拆成 1–4 个必须出现的事实串，看 top-3 拼起来覆盖了几个。概览型的失败形态是「拼不全」，用 hit@k 量不出来（文档命中但只命中一个片段也算 1.0） |
| 事实串口径 | 只取 **chunk 命中数 ≤ 3** 的串。`Milvus`(54 块)、`校验`(23 块)、`决策管线`(15 块) 这类词几乎每块都有，拿它们当事实点等于没量 |
| 脚本 | `backend/scripts/probe_retrieval_stages.py`；原始数据 [stage-probe-2026-11-03.json](stage-probe-2026-11-03.json) |

## 2. 结果

### 2.1 逐级名次：答案片段在哪一级丢掉

名次 = 候选池里第一个含答案片段的片段位置（`—` = 这一级就没捞到）。

| 题型 | 问题 | sparse@20 | dense@20 | 融合后 | 覆盖率 top-3 |
|---|---|---|---|---|---|
| 概览 | 系统由哪些部分组成，请求怎么流转？ | — | 8 | **16** | 0.00 |
| 概览 | 优雅停机怎么做？为什么需要？ | 3 | 1 | 1 | 0.50 |
| 概览 | 监控哪些指标、有哪些告警？ | 16 | 13 | **13** | 0.00 |
| 概览 | 备份怎么恢复？恢复后确认什么？ | 1 | 10 | 3 | 0.33 |
| 细节 | 为什么要给 NLTK 语料单独放进镜像？ | 1 | 1 | 1 | 0.50 |
| 细节 | ScrapeTargetDown 是什么意思？ | 1 | 1 | 1 | 1.00 |
| 细节 | 改完告警规则怎么生效？ | 3 | 2 | 2 | 1.00 |
| 细节 | 数据库迁移怎么执行？ | 2 | 4 | 2 | 1.00 |

**dense 单通道 4/4 都把答案捞进了 20 条池里**（名次 1–13），说明召回通道本身没问题。
问题是融合把答案**往下压**（系统组成：dense 8 → 融合 16；备份恢复：dense 10 → 融合 3 是唯一变好的），
而生产只看融合后的前 3 条。

### 2.2 四个候选修法的实测

| 变体 | 概览（4 题） | 细节（4 题） | 结论 |
|---|---|---|---|
| **现状**（窗口 3 → top-3） | **0.21** | **0.88** | 基线 |
| 重排窗口 3 → 10 → 20 | 0.21 / 0.21 / 0.21 | 0.88 / 0.88 / 0.88 | **完全无变化** |
| 剔除目录块 | 0.21 | 0.88 | 无变化 |
| **邻块回填 ±1（同标题）** | **0.27** | **1.00** | 唯一正向，上下文 1280/1454 字符 |
| 去冗余（同标题最多 1 名额） | 0.14 | 0.88 | **更差** |
| 去冗余 + 邻块 | 0.14 | 0.88 | 更差 |

三条被推翻的猜想：

1. **「窗口太窄，重排没机会看到正确答案」——错。** 把窗口从 3 拉到 20，每一道题的覆盖率数字**一位不差**。
   答案片段在池里（融合第 13/16 名），但重排仍然把它排到第 4 名之后。
   顺带一个代价数字：窗口 20 要重排 20 对，CPU 上 **2.37s/题**；窗口 3 只要 ~0.4s。
2. **「去冗余能救『只列 3 个指标』」——错，反而更差。** 强制每个章节只占 1 个名额后，
   优雅停机从 0.50 掉到 0.25：它的答案本来就是**同一章节的相邻两块**，去冗余把第二块挤走了。
3. **「目录块占名额」——方向对但量不出来。** 剔除后覆盖率不变（腾出的名额被另一条无关块填上）。
   全语料只有 1 个目录块（`deployment.md#0`），它确实拿了 0.9556 进过 top-3，但剔除它换不回答案。

### 2.3 机制：为什么概览题拼不全

看 top-3 到底选中了什么（`优雅停机` 题）：

```
0.0137  deployment.md#42  2.2.2 关机与升级语义（P0-4）   ← 对：SIGTERM 那张表
0.0110  architecture.md#23  3.x 熔断、用量与成本（P2.1）  ← 无关
0.0034  monitoring.md#61  6.1 每日一致性巡检              ← 无关
```

三个机制，都是**结构问题**，不是模型不敏感：

- **① 答案跨章节，chunk 级 top-3 装不下。** 「优雅停机」的答案分布在 §2.2.2 的表格（时间预算）
  和相邻正文（为什么需要）里；「系统组成」横跨 §2 服务拓扑和 §3 决策管线。
  3 个 512 字符的碎片，无论怎么选都拼不出一段完整说明。
- **② 表格行级切分让 3 个名额换 3 行表格。** 「监控哪些指标、有哪些告警」的 top-3 是
  `deployment.md#224 / #227 / #228` —— **同一张指标表的三行**（score 0.9700 / 0.9693 / 0.9678）。
  这是端到端验证里「只列 3 个指标、12 条告警一条没提」的**直接原因**：告警在另一张表里，
  三个名额全给了指标表，永远轮不到。行级切分本身是对的（「X1 的重量」这种点查靠它），
  错的是**命中一行时不回填整表**。
- **③ 重排分数不可跨题比较。** 答案在池里的题 top1 只有 0.0137–0.33，答案**不在**池里的题 top1 反而是
  0.97–0.99。因为后者选中的是「结构上像答案」的块（指标单行、目录），它们与问句字面高度重合却没有内容。
  所以 `KB_RELEVANCE_SCORE_THRESHOLD=0.3` 在概览题上不是「太严」也不是「太松」——
  它拿一个跨题不可比的量当判据，本来就不该用来区分这两种情况。

## 3. 两个题目自身的问题（自我纠错）

| 问题 | 原判 | 实际 |
|---|---|---|
| 生产环境怎么部署？ | 三级全 `—`，判为召回失败 | **是我选错了 ground truth**。事实串落在 §2.1 场景表的脚注里，而系统三轮都召回了 §4「生产环境部署」。同一问题在文档里有两处答案，题面有歧义 |
| 怎么查看 PostgreSQL 指标？ | 同上 | **语料没写这件事**。`monitoring.md` 讲的是 exporter target 配置，`pg_stat_activity` 只出现在 backup-restore 的验收步骤。题目超出语料 |

两题已在脚本里标 `valid: false`，不计入汇总——把「我的标注错误」算成系统缺陷，
会让人去修一个不存在的问题。

## 4. 结论

1. **「rerank 对宽泛问句不敏感」这个解释不成立。** 给重排 3 条还是 20 条候选，结果一模一样；
   真正的分界在**融合之后只有 3 条进上下文**，而答案分散在多个章节。
2. **本轮不改生产配置。** 唯一正向的「邻块回填」在 8 道有效题上是 +0.06 / +0.12 个事实点，
   按本项目自己的方法学（P1-5：1 题 = 1.19–1.56pp，检测 6pp 需 100 题）**完全在噪声里**。
   加宽重排窗口代价明确（+2s/题）而收益为 0，更不能上。
3. **要真正解决概览题，得改召回单元，而不是调参数。** 方向是章节级召回：
   以 h2/h3 为召回单元（或把同标题下的连续块作为一个整体参与重排），
   再把命中的章节展开成完整上下文。这是结构性改动，**必须先有能分辨的评测集**——
   概览题在 90 题里只有 4–5 道，任何 A/B 都会被单题波动淹没。
4. **表格回填是独立且低风险的一项。** 「命中一行 → 回填整张表」不改变排序，只改上下文组装，
   但它同样需要 ≥40 道「列举型」题目才能验证。已列入待办，不作为本轮交付。

## 5. 复现

```bash
cd backend
# 只看到召回与融合两级（不需要重排模型，约 1 分钟）
uv run python scripts/probe_retrieval_stages.py --skip-rerank

# 完整三级 + 四个变体（需 ollama serve 与 bge-m3，重排走本地 HF 缓存）
uv run python scripts/probe_retrieval_stages.py --rerank-n 3,10,20 \
    --report ../docs/benchmarks/stage-probe-2026-11-03.json
```

纯函数（目录识别 / 邻块扩展 / 覆盖率）有单元测试：`tests/evaluation/test_stage_probe.py`。
脚本**不进 CI**（依赖本机 Ollama 与 1GB 重排模型）；CI 的卡点仍是 `run_eval.py`。
