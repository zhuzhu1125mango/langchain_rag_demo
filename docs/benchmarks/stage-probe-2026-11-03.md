# 概览型问题丢在哪一级：检索逐级探针（2026-11-03）

> 端到端验证（[e2e-verification-2026-11-03.md](../e2e-verification-2026-11-03.md)）的结论是
> 「问题越大越差」，当时给的解释是 **rerank 对宽泛问句不敏感**。
> 这个解释**没有证据**：生产 trace 只存了 rerank 之后的 top-3（`KB_HYBRID_RERANK_TOP_K=3`），
> 我们看到的 0.077 / 0.009 是「3 条候选里最好的」，不是「20 条候选里最好的」。
>
> 两种故障的修法完全相反——池里没有（改召回）vs 池里有但被挤出（改融合/窗口）。
> 这份报告把三级摊开，逐级定位，并用 24 道题把四个候选修法逐个测掉。

## 1. 怎么测的

| 项 | 内容 |
|---|---|
| 语料 | 与端到端验证同一批 4 份真实文档，**生产切分器**（`ChunkingFactory`，`CHUNK_SIZE=512 / OVERLAP=64`）→ **502 个 chunk**（architecture 71 / deployment 296 / backup-restore 72 / monitoring 63） |
| 通道 | sparse = BM25（同生产 jieba 分析器）；dense = Ollama `bge-m3`；融合 = RRF（k=60，等权）；重排 = `bge-reranker-base`（`max_length=256`，CPU） |
| 题目 | **24 道：概览 12 + 细节 12**（题干沿用端到端验证的 10 道，另补 14 道覆盖部署/回滚/容量/巡检/流式） |
| 指标 | **事实点覆盖率**：把答案拆成 1–4 个必须出现的事实串，看 top-3 拼起来覆盖了几个。概览型的失败形态是「拼不全」，用 hit@k 量不出来（文档命中但只命中一个片段也算 1.0） |
| 事实串口径 | 只取 **chunk 命中数 ≤ 8** 的串。502 个 chunk 下 df=8 只占 1.6%（每条候选约 1.6% 概率白送一个「命中」），而 `Milvus`(54)、`端口`(56)、`校验`(23) 这类词意味着 11% 以上，等于没量 |
| 脚本 | `backend/scripts/probe_retrieval_stages.py`；原始数据 [stage-probe-2026-11-03.json](stage-probe-2026-11-03.json) |

**为什么从 10 题加到 24 题**：10 道题时 1 题 = 10pp，任何差异都读不出显著性，
而「章节级召回」这类改动的预期收益就在 5–10pp。24 道时 1 题 ≈ 4.2pp，才开始能分辨。

## 2. 结果

### 2.1 三级命中：答案片段在哪一级还在

| 题型 | sparse@20 有答案 | dense@20 有答案 | 融合后还在 | 进生产窗口(3) |
|---|---|---|---|---|
| 概览（12） | 11 | 11 | **12** | 10 |
| 细节（12） | 11 | 12 | **12** | 10 |

**召回通道基本没问题**（dense 单通道 11–12/12 捞得到），融合也没丢（24/24 都在池里）。
丢的是「进 top-3」这一步：各 2 题被挤出去。三个具体案例分别对应不同层级：

| 问题 | 现象 | 丢在哪一级 |
|---|---|---|
| 系统由哪些部分组成，请求怎么流转？ | dense 第 8 → 融合第 **16**；重排窗口 20 时答案块排第 6 | **融合**把 dense 捞到的东西压下去 |
| 备份恢复后要确认哪些事？ | dense 第 **1** → 融合第 **12** | 同上（dense 排第一的块被 RRF 沉底） |
| 换 Embedding 模型需要做什么？ | 融合第 7，窗口 20 也给了机会 | **重排**把它埋到 3 名外 |

### 2.2 四个候选修法（24 题实测）

均值是事实点覆盖率；Δ 是与现状（窗口 3、top-3）的逐题差；变好/变差是题数。

| 变体 | 概览（12） | 细节（12） | 逐题方向 | 结论 |
|---|---|---|---|---|
| **现状** | **0.598** | **0.792** | — | 基线 |
| 重排窗口 → 10 | 0.542（Δ −0.055） | 0.792（Δ 0） | 概览 2 好 2 坏 | 无收益 |
| 重排窗口 → 20 | 0.501（Δ **−0.097**） | 0.792（Δ 0） | 概览 1 好 2 坏 | **负向**，且 2.47s/题 |
| 剔除目录块 | 0.598 | 0.792 | 0 | 量不出差别 |
| **邻块回填 ±1（同标题）** | **0.618**（Δ +0.021） | **0.833**（Δ +0.042） | 2 好 **0 坏** | 唯一非负 |
| 去冗余（同标题最多 1 名额） | 0.452（Δ **−0.146**） | 0.792（Δ 0） | 概览 1 好 **4 坏** | 明确有害 |

三条被推翻的猜想：

1. **「窗口太窄，重排没机会看到正确答案」——错，而且加宽是负向的。**
   概览题从 0.598 掉到 0.542 / 0.501。原因不是重排更准了，而是**窗口越大，塞进来的
   「字面很像但不是答案」的块越多**（指标单行、目录、配置对比表），重排在没有章节上下文时
   更偏爱它们，把它们顶到前面，反而挤掉了原本对的那块。
   最典型：「生产环境升级换版本要注意什么」窗口 3 时 1.00，窗口 10 就掉到 0.50。
   代价也明确：24 题重排 20 个候选共 **59.2s**，即 **2.47s/题**（窗口 3 按同单价约 0.4s）。
2. **「去冗余能救『只列 3 个指标』」——错，明确有害**（概览 −0.146，4 题变差 1 题变好）。
   优雅停机从 0.50 掉到 0.25：它的答案本来就是**同一章节的相邻两块**，去冗余把第二块挤走了。
3. **「目录块占名额」——方向对但量不出来。** 剔除后覆盖率一位不差。全语料只有 1 个目录块
   （`deployment.md#0`），它确实拿了 0.9556 进过 top-3，但剔除它换不回答案。

### 2.3 机制：为什么概览题拼不全

看 top-3 到底选中了什么（`优雅停机` 题）：

```
0.0137  deployment.md#42  2.2.2 关机与升级语义（P0-4）   ← 对：SIGTERM 那张表
0.0110  architecture.md#23  3.x 熔断、用量与成本（P2.1）  ← 无关
0.0034  monitoring.md#61  6.1 每日一致性巡检              ← 无关
```

三个机制，都是**结构问题**，不是模型不敏感：

- **① 答案跨章节，chunk 级 top-3 装不下。** 「优雅停机」的答案分布在 §2.2.2 的表格（时间预算）
  和相邻正文（为什么需要）里；「系统组成」横跨 §2 服务拓扑和 §3 决策管线。
  3 个 512 字符的碎片，无论怎么选都拼不出一段完整说明。
- **② 表格行级切分让 3 个名额换 3 行同一张表。** 「监控哪些指标、有哪些告警」的 top-3 是
  `deployment.md#224 / #227 / #228` —— **同一张指标表的三行**（score 0.9700 / 0.9693 / 0.9678），
  覆盖率 0.00。这是端到端验证里「只列 3 个指标、12 条告警一条没提」的**直接原因**：
  告警在另一张表里，三个名额全给了指标表，永远轮不到。行级切分本身是对的
  （「X1 的重量」这种点查靠它），错的是**命中一行时不回填整表**。
- **③ 重排分数不可跨题比较。** 答案在池里的题 top1 只有 0.0137–0.33，答案**不在**池里的题 top1
  反而是 0.97–0.99。因为后者选中的是「结构上像答案」的块（指标单行、目录），它们与问句字面
  高度重合却没有内容。所以 `KB_RELEVANCE_SCORE_THRESHOLD=0.3` 在概览题上不是「太严」也不是
  「太松」——它拿一个跨题不可比的量当判据，本来就不该用来区分这两种情况。

## 3. 两次自我纠错

| 问题 | 原来的判断 | 纠正 |
|---|---|---|
| 生产环境怎么部署？ | 三级全 `—`，判为召回失败 | **ground truth 选偏**：事实串落在 §2.1 场景表的脚注里，而系统三轮都召回了 §4「生产环境部署」。同一问题有两处答案，题面有歧义 → 已改写为「从零部署一套生产环境要做哪些事」并重选事实串 |
| 怎么查看 PostgreSQL 指标？ | 同上 | **语料没写这件事**：`monitoring.md` 讲的是 exporter target 配置，`pg_stat_activity` 只出现在 backup-restore 的验收步骤 → 已移出题集 |
| **概览题覆盖率 0.21** | 10 题版的核心数字 | **样本偏差**：那 4 道概览题是从端到端验证的失败案例里挑的（专门挑了最难的），不是随机样本。扩到 12 道后是 **0.598**，与细节题 0.792 的差距远没有 4 倍那么大 |

第三条是这轮最重要的纠正：**用「已知失败的案例」当评测集，量出来的是失败案例的难度，
不是系统的平均水平。** 这也解释了为什么 10 题版会得出「重排窗口加宽无变化」这种过于温和的结论
——样本太小，方向信号被两三个极端题盖住了。

## 4. 结论

1. **「rerank 对宽泛问句不敏感」不成立。** 给重排 3 条还是 20 条，细节题一位不差、
   概览题反而变差；真正的分界在**融合之后只有 3 条进上下文**，而答案分散在多个章节。
2. **本轮仍不改生产配置。** 唯一非负的「邻块回填」在 24 题上是 +0.021 / +0.042，
   2 题变好 0 题变差——方向一致但样本还撑不起显著性（符号检验 p=0.25）。
   加宽窗口（负向 + 2.47s/题）和去冗余（−0.146）已被排除。
3. **要真正解决概览题，得改召回单元，而不是调参数。** 方向是章节级召回：
   以 h2/h3 为召回单元（或把同标题下的连续块作为一个整体参与重排），
   再把命中的章节展开成完整上下文。24 道题已经能分辨 4pp 的差异，够做这个 A/B 了。
4. **表格回填是独立且低风险的一项**（机制②）：命中一行 → 回填整张表，不改变排序，
   只改上下文组装。它与邻块回填共用同一套「按 chunk_index 取邻居」的能力，
   建议一起实现、一起 A/B。

## 5. 复现

```bash
cd backend
# 只看到召回与融合两级（不需要重排模型，约 1 分钟）
uv run python scripts/probe_retrieval_stages.py --skip-rerank

# 完整三级 + 四个变体（需 ollama serve 与 bge-m3，重排走本地 HF 缓存；24 题约 2 分钟）
uv run python scripts/probe_retrieval_stages.py --rerank-n 3,10,20 \
    --report ../docs/benchmarks/stage-probe-2026-11-03.json
```

纯函数（目录识别 / 邻块扩展 / 覆盖率）有单元测试：`tests/evaluation/test_stage_probe.py`。
脚本**不进 CI**（依赖本机 Ollama 与 1GB 重排模型）；CI 的卡点仍是 `run_eval.py`。
