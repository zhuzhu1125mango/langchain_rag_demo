# 生产索引上的逐级探针（2026-11-10）

> 一句话：**本地探针不是替身，它就是线上**。24 题、同一套事实点、同样 4 道零覆盖题，
> 放宽窗口后同样多坏 2 题 —— 之前基于本地夹具的取舍（不调大窗口、不上去重、
> 优先低置信兜底）在生产上同样成立。

## 1. 为什么还有这一份

前一份探针（[stage-probe-2026-11-10.md](stage-probe-2026-11-10.md)）在**仓库文档上自建索引**：
好处是能随意换切片、换融合、换选择规则；代价是它测的从来不是「线上那套索引 + 那套参数」。

2026-11-10 重灌之后，生产语料与探针语料**终于同源**（同样 4 篇文档、同一切分器、同样 606 块），
本地结论第一次可以直接对到线上。既然能对，就不该假设。

两者唯一的差别只剩索引来源与运行期条件（KB 过滤、真实提问措辞）。

## 2. 口径

| 项 | 值 |
|---|---|
| 索引 | 生产 `documents` 集合，**606 块**（重灌后） |
| 通道 | dense(bge-m3) + sparse(BM25，词表 3633 词) |
| 融合 | RRF `k=60`，两路各取 20 |
| 重排 | `BAAI/bge-reranker-base`，窗口 **N**（扫描 3/5/10/20），取前 3 |
| 生产实际 | 窗口 = `max(k, KB_HYBRID_RERANK_TOP_K=3)` → **3**，重排只能在 RRF 前 3 名里排序 |
| 题集 | 与本地探针**同一批 24 题**（概览 12 / 细节 12）、同一套事实点、同一个覆盖率函数 |
| 脚本 | `backend/scripts/probe_prod_stages.py`（只读；不写 Milvus、不改配置、不重启） |

工具是照抄生产 `search_hybrid` 的顺序实现的：两路并行召回 → RRF → `fused[:N]` → 重排 → 取 k。
区别只在把 N 当变量扫描。

## 3. 结果：与本地逐位一致

事实点覆盖率（top-3 拼起来覆盖几个事实点）：

| 配置 | 概览(12) | 细节(12) |
|---|---|---|
| **生产等价**：窗口 3 / 最终 3 | **0.556** | **0.792** |
| 窗口 5 | 0.535 | 0.792 |
| 窗口 10 | 0.535 | 0.792 |
| 窗口 20 | **0.451** | 0.792 |

对照本地探针：0.556 / 0.535 / 0.535 / 0.452 与 0.792 ×4 —— 差异只在第四位小数（逐题四舍五入所致）。

更强的证据是**逐题对齐**：

- n3 下 24 题里 **21 题数值完全相同**，另 3 题只是两位 vs 三位小数的写法差异
  （0.67 vs 0.667、0.33 vs 0.333），命中事实点实际一致；
- **零覆盖题两个口径是同一组**：n3 都是 4 题（系统组成部分 / 监控指标告警 /
  换 Embedding 模型 / 备份恢复后确认），n20 都是 6 题（多出迁移回滚、生产升级换版本）；
- 邻块回填同样只值约 1 题：概览 0.556 → 0.597（+4.1pp）、细节 0.792 → 0.833（+4.2pp）。

## 4. 只有生产能给出的三个数

| 指标 | 概览 | 细节 |
|---|---|---|
| 候选池（融合 top-20 的覆盖率） | 0.792 | **1.000** |
| 答案片段落在融合 top-10 内 | 10/12 | 11/12 |
| **dense 单通道 top-3** | 0.458 | **0.875** |
| **sparse 单通道 top-3** | 0.340 | **0.625** |

三点解读：

1. **候选池不是瓶颈**（细节题答案 100% 在池子里），和本地一致；
2. **稀疏通道在本语料上明显弱于 dense**（0.340 vs 0.458、0.625 vs 0.875）。
   这解释了 A/B 里「等权 hybrid 反而不如 dense」——给弱通道 50% 权重，口语题上的
   错误头部会被「两路共同认可」顶上来。这是方向一致的两份独立证据；
3. 泛问的失败点仍然集中在「重排怎么选这 3 块」，不是「捞不到」。

## 5. 结论

1. **本地夹具可以信**：同一批题、同一个覆盖率定义，在自建索引和生产索引上给出同一组数字。
   以后做选择规则实验，不必每次占用生产；
2. **「不要调大 `KB_HYBRID_RERANK_TOP_K`」在线上成立**：3 → 20 概览 −10.5pp，
   而且多坏的两道题与本地是同样两道；
3. **泛问仍是那 4 道**，失败机制（重排分崩塌 / 同表三行吃满名额 / 术语缺口）没有变化，
   本次没有引入新的失败模式 —— 重灌没有让检索变差，也没有让泛问变好；
4. 下一步优先级不变：低置信兜底（top1 < 0.15 不硬答）→ 表格感知选择；
   继续调窗口/融合权重已被两份独立实验否定。

## 6. 边界（不要超读）

- 24 题，**1 题 = 4.2pp**；两次口径之间的任何 ≤1 题差异都在噪声内；
- 事实点是**字面串**（`intent_router`、`ScrapeTargetDown` 这类），对同义改写不敏感，
  因此「覆盖率」量的是「答到了几个点」，不是「答得对不对」；
- 生产知识库只有这 4 篇文档，且与探针语料同源 —— 换一批文档这个等价关系需要重新验证，
  不能默认成立；
- 一次跑 **8 分 49 秒**（CPU，24 题 × 4 次重排）。它适合做一次性的口径确认，
  不适合放进每次都跑的夜间门禁。

## 7. 复现

```bash
docker cp backend/scripts/probe_prod_stages.py backend-prod:/app/scripts/
docker exec backend-prod python scripts/probe_prod_stages.py \
  --report /app/data/probe-prod-20261110.json
```

数据：`backend/data/probe-prod-20261110.json`（含逐题 picked、重排分、融合名次），
与本地 `docs/benchmarks/stage-probe-2026-11-10.json` 可直接逐题比对。
