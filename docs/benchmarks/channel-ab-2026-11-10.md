# 检索通道 A/B 重跑（2026-11-10）：先确认口径，再看数字

> 触发原因：11-09 修掉了「BM25 词表在 5 条演练文本上冻结」的部署事故，11-02 的
> 通道结论被标注「重跑前不应引用」。这次重跑要回答三个问题：
>
> 1. 11-02 的数字还能不能复现？
> 2. 那次事故到底损失了多少召回？
> 3. 稀疏通道修好之后，生产该不该改融合策略？

## 0. 结论

| 问题 | 答案 |
|---|---|
| 11-02 能复现吗 | ✅ **12 个臂的 hit@3 / MRR 逐位相同**（见 §2） |
| 11-02 受事故影响吗 | ❌ **不受影响**：脚本在评测语料本体上 fit BM25，从不读生产索引（见 §1） |
| 事故损失多少 | sparse hit@3 **0.786 → 0.036**，63 题对 0 题，p < 0.001（见 §3） |
| 修复后 hybrid 变好吗 | ❌ **反而低 5.95pp**（0.941 → 0.881），但 p = 0.125，在噪声内（见 §3、§4） |
| 该改生产配置吗 | ❌ **不改**：没有显著证据；这份 84 题 / 78 篇合成语料不足以支撑生产变更 |

最重要的一句话：**「索引修好了」不等于「检索变好了」，这两件事必须分开说。**

## 1. 先把口径查清楚（这是上次没做的事）

`run_channel_ab.py` 的 sparse 臂走 `run_eval.build_index(corpus)`：在
`eval_corpus.jsonl` 的 78 篇文档上 `fit` 一次 BM25，再用同一份词表编码查询。
也就是说：

- 它测的是**通道的算法差异**；
- 它**测不到**「生产词表冻结」这类部署故障——那次故障只发生在生产 Milvus 的
  持久化词表上，而这份脚本根本没有连 Milvus。

11-02 的报告当时没写清执行路径，所以只敢标注「未测、重跑前勿引用」。现在读代码
可以确认：**那三行 hybrid/dense/并集相同，不是稀疏为空导致的，而是重排把这几个
候选池收敛到了同一组文档**。这个解释和「事故」无关，两者是独立问题。

为了让事故可复现，本次给脚本加了 `--sparse-vocab <词表文件>`：用外部词表编码，
并严格按生产语义处理空查询向量（**整条通道跳过**，而不是让全零向量排出一堆并列
0 分的无关文档）。不这样做，算出来的不是事故损失，是另一种故障。

## 2. 复现性：12 个臂逐位相同

同一份 `kb_eval_dataset.jsonl`（90 题，84 道有答案）/ `eval_corpus.jsonl`（78 篇），
`--top-k 3 --channel-top-k 20`，与 11-02 完全同口径。

| arm | 11-02 hit@3 | 11-10 hit@3 | 11-02 MRR | 11-10 MRR |
|---|---|---|---|---|
| sparse | 0.786 | **0.786** | 0.720 | **0.720** |
| dense | 0.941 | **0.941** | 0.905 | **0.905** |
| hybrid (RRF k=60) | 0.881 | **0.881** | 0.788 | **0.788** |
| wrrf50 | 0.881 | **0.881** | 0.788 | **0.788** |
| sfuse50 | 0.881 | **0.881** | 0.807 | **0.807** |
| wrrf70 | 0.881 | **0.881** | 0.825 | **0.825** |
| sfuse70 | 0.941 | **0.941** | 0.849 | **0.849** |
| wrrf85 | 0.917 | **0.917** | 0.863 | **0.863** |
| sfuse85 | 0.952 | **0.952** | 0.895 | **0.895** |
| hybrid+rerank | 0.917 | **0.917** | 0.883 | **0.883** |
| dense+rerank | 0.917 | **0.917** | 0.883 | **0.883** |
| union+rerank | 0.917 | **0.917** | 0.883 | **0.883** |

逐位一致说明两件事：评测链路是确定性的（没有随机种子、没有采样），
以及 11-02 与本轮之间**没有代码或数据漂移**。

## 3. 把事故复现出来：sparse 0.786 → 0.036

用事故现场的旧词表（59 词、`corpus_size=5`，备份文件
`bm25_documents.json.bak.20261109-073555`）编码同一份评测语料：

| arm | 健康词表 | 冻结词表 | Δ | 不一致对 | McNemar p |
|---|---|---|---|---|---|
| sparse | 0.786 | **0.036** | −75.00pp | 63 : 0 | < 0.001 ✅ |
| dense | 0.941 | 0.941 | 0 | — | — |
| hybrid | 0.881 | **0.941** | +5.95pp | 6 : 1 | 0.125 |

两件事同时被证实：

1. **稀疏通道当时确实是死的**：84 道里只剩 3 题命中，且都是「删除/演练」这类
   刚好在旧词表里的词；真实制度问题（请假、年终奖、年假）一题不中。
2. **混合检索当时等价于 dense**：稀疏返回空 → RRF 只剩一路 → 排序与 dense 相同。
   0.036 的稀疏臂没有污染结果，因为它在查询阶段就被跳过了。

这就是「事故损失」与「检索质量」分离的地方：**损失的是一个召回通道，
不是准确率**。dense 一直在兜底，所以用户没有感知到明显故障。

## 4. 反直觉的部分：修好之后 hybrid 反而更低

| arm | hit@3 | 口语(20) | 精确匹配(20) |
|---|---|---|---|
| dense | 0.941 | 0.750 | 1.000 |
| hybrid（健康稀疏） | 0.881 | 0.500 | 1.000 |
| hybrid（冻结稀疏） | 0.941 | 0.750 | 1.000 |
| sfuse85 | 0.952 | 0.800 | 1.000 |

机制不复杂：等权 RRF 给两路各 50% 权重，而 sparse 在口语化题上只有 0.30
（dense 0.75）。**一个弱通道的错误头部会被当成「两路共同认可」顶上来**——
11-02 的 `weighted_rrf_fuse` 注释里已经写过这个假设，现在有了实测：
给 dense 85% 权重（`sfuse85`）能回到 0.952。

但必须克制：

- hybrid vs hybrid(冻结) 的 6:1，p = 0.125，**不显著**；
- sfuse85 vs dense 只多 1 题，p = 1.0，**更不显著**；
- 84 道题里 1 题 = 1.19pp，这份语料支撑不了「换融合策略」这种生产变更。

## 5. 建议

1. **不改生产配置。** 与 11-02 的结论一致，但理由更新了：不是「没证据说更差」，
   而是「修复让一个已知较弱的通道真正参与进来，方向上可能变差，但证据不足以量化」。
2. **想改就改融合权重，不是改召回。** 候选方案是 dense 主导的分数融合
   （`sfuse85`，0.952），代价是代码改动 + 需要更大题量支撑（按 11-02 §3 的估算）。
3. **生产侧先观察，不急于动手。** 现在 hybrid 真的用上 sparse 了，口语化/泛问的
   候选池会变。用 `request_traces` 对比修复前后同类问题的 top-3 命中，比拿合成语料
   直接改线上更可靠。
4. 如果只想保留「修复」的好处、避免「融合变差」的风险，最小动作是**当前不动**：
   hybrid+rerank 0.917 与 dense+rerank 0.917 完全相同，生产没有因为这次修复立刻变坏
   （重排把融合差异吸收掉了）。

## 6. 复现命令

```bash
cd backend

.venv/Scripts/python.exe scripts/run_channel_ab.py --top-k 3 \

  --report ../docs/benchmarks/channel-ab-frozen-vocab-2026-11-10.json

# 显著性（跨报告比较用 ab_significance.load_arm + compare）
.venv/Scripts/python.exe scripts/ab_significance.py \
  --report ../docs/benchmarks/channel-ab-2026-11-10.json --pairs "dense:hybrid,dense:sfuse85"
```

## 7. 这份报告的边界

- 语料是 **78 篇合成/整理文档**，不是生产那 532 条真实切片；结论只对这份语料成立。
- 评测是**文档级 hit@3**，不衡量答案质量；重排会把融合差异吸收掉，端到端影响更小。
- 冻结词表复现用的是**同一份旧词表文件**，但它编码的是评测语料，不是生产语料；
  它证明的是「词表与语料不匹配时通道会死」，不是「生产当时的具体命中率」。
