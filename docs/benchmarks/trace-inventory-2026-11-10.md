# 生产轨迹盘点（2026-11-10）：为什么它撑不起 100 题评测集

> 起因：24 题探针的分辨率是 4.2pp/题，读不出 5~6pp 的差异。原计划从
> `request_traces` 捞真实提问把题量做到 ~100。盘点后这个计划不成立。

## 1. 规模

| 指标 | 值 |
|---|---|
| 轨迹总数 | **73** |
| 去重问题 | **47** |
| 会话数 | 59 |
| 用户数 | 4 |
| 时间范围 | 2026-10-08 ~ 2026-11-08 |
| 有 KB 结果的轨迹 | **12** |

一个月的真实流量只有 73 条，其中一半集中在两天（10-12 的 22 条、11-03 的 14 条），
基本是自测与演练，不是持续的用户流量。

## 2. 47 条去重问题的构成

| 类型 | 条数 | 说明 |
|---|---|---|
| 产品型号（智星 X1） | **21** | 生产知识库里**没有产品文档**，这些题必然 `kb=0`，不可用于检索标注 |
| 闲聊 / 通用知识 / 天气 | 10 | 「你好」「北京天气」「什么是向量数据库」，不经过 KB |
| 项目文档 | **16** | 唯一可标注的部分，但见下 |

16 条项目文档题里，按意图去重后只剩 **约 9 个意图**：

- 系统组成与请求流转、优雅停机、监控指标/告警、备份恢复（×3 种问法）、
  数据库迁移、告警规则生效（×2）、NLTK 语料（×2）、ScrapeTargetDown（×2）、
  PostgreSQL 指标查看。

其中 **7 个意图与现有 24 题探针重合**（系统组成、优雅停机、监控告警、备份恢复、
迁移执行、告警生效、NLTK、ScrapeTargetDown），真正的新意图只有 1~2 个。

## 3. 结论

- **轨迹不能扩题**：最多贡献 ~9 个意图，且大部分已被 24 题覆盖；
  100 题必须**从文档人工/半自动生成**，不是「捞真实提问」。
- **产品型号题是分布信号，不是评测素材**：真实流量里 21/47 在问智星 X1，
  而生产知识库只有 4 篇项目文档。要么补产品文档，要么接受这些问题永远 `kb_miss`。
- 顺带发现：**生产知识库与仓库文档不一致**。生产是 11-04 入库的 532 块；
  仓库同 4 篇文档用当前切分器切出 **606 块**（+14%）。差异可能来自文档更新
  （如今天新增的 `deployment.md` §7.8）或切分器版本变化，**未逐篇比对**。
  无论哪种，都说明「文档改了、KB 没重灌」这件事需要一次确认。

## 4. 如果还要扩题，成本最低的做法

不要均匀扩到 100 题，而是**按失败模式分层**（每类 10 题，共 40 题）：

| 子集 | 取材 | 判据 |
|---|---|---|
| 多面向列举（指标+告警、组成+流转） | 现有 4 篇文档的表格与小节 | 修复后该子集覆盖率 +20pp |
| 表格行枚举（告警表、端口表、参数表） | 同上 | 同上 |
| 术语缺口（口语问法 vs 文档术语） | 用 trace 里的真实问法改写 | 同上 |
| 代码块/结构块（代码地图、管线图） | `architecture.md` | 同上 |

子集 n=10 时 1 题 = 10pp，只有「结构性修复」才读得出来——这正好符合我们的目的：
**不追 5pp 的调参差异，只判断某个机制性改动有没有用。**

预计成本：自动生成候选（按 heading 切片出题）0.5h + 人工确认 golden/事实串 1.5h。

## 5. 复现

import asyncio
from sqlalchemy import text
from src.database import async_session_maker

async def main():
    async with async_session_maker() as db:
        rows = (await db.execute(text(
            "select question, count(*) n, max(primary_mode) m from request_traces group by 1 order by n desc"
        ))).fetchall()
        for r in rows:
            print(r.n, r.m, r.question)

asyncio.run(main())
PY
