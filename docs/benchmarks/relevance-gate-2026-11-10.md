# 低置信兜底（top1 < 0.15 不硬答）：离线验证失败

> 结论先说：**这个改动不该上。** 重排分数与「答得对不对」无关——
> 失败题的 top1 从 0.12 到 0.97，而一道**完全答对**的题 top1 只有 0.019。
> 任何阈值都会同时拒掉能答的题，且拦不住真正答错的题。
> 落地的是另一件仍然成立的事：**拒答留痕**。

## 1. 这项改动本来是什么

线上早就有这道判定，叫 `KB_RELEVANCE_SCORE_THRESHOLD`（默认 **0.3**）：
最终选中的片段按 `rerank_score` 跟阈值比，全都低于阈值 → 清空上下文 →
`KB_MISS_TEMPLATE` 显式说「知识库里没有找到相关内容」。

所以「低置信兜底 top1 < 0.15」不是新增机制，**只是把同一个数字从 0.3 改成 0.15**。
那它值不值得改，就变成一个能用现有数据回答的问题。

## 2. 怎么验的

`backend/scripts/eval_relevance_gate.py` 直接读探针报告里的逐题数据（选中的 3 块、
每块的 `rerank_score`、该题的事实点覆盖率），按生产 `_calculate_relevance` 的真实
判定（`any(score >= t) or avg >= t`）模拟门禁，扫一遍阈值。

两个独立数据源：生产索引探针（`probe-prod-20261110.json`）与本地探针
（`stage-probe-2026-11-10.json`）——**给出逐行完全相同的表**，这同时验证了评估器本身。

判据不是「拒得多不多」，而是：

- **误拒**＝覆盖率 > 0 却被判不相关 → 能回答却拒答；
- **漏拒**＝覆盖率 = 0（三块拼起来一个事实点都没答到）却放行 → 本该拒答却硬答。

## 3. 扫描结果（24 题，其中「该拒」4 题）

| 阈值 | 拒答 | **误拒** | 漏拒 | 放行 |
|---|---|---|---|---|
| 0.00（等于关掉） | 0 | 0 | 4 | 24 |
| 0.05 / 0.10 | 1 | **1** | 4 | 23 |
| **0.15**（提案值） | 2 | **1** | 3 | 22 |
| **0.30**（当前生产） | 3 | **2** | 3 | 21 |
| 0.50 | 7 | **6** | 3 | 17 |
| 0.90 | 13 | **10** | 1 | 11 |

三件事直接读出来：

1. **0.15 比 0.30 好一点，但好错了方向。** 少拒的那道是「从零部署一套生产环境」
   （top1 0.259、覆盖率 0.67，本来就该回答）。**该拒的仍只拒掉 1 道（系统组成部分）。**
2. **真正的失败题拦不住。** 它们的 top1 是 **0.705 / 0.775 / 0.970** ——
   分数越高、错得越自信，这恰恰是「低置信兜底」这个思路的反面。
3. **被误杀的那道题答得完全正确。** 「熔断触发的时间和条件」top1 = **0.019**、
   覆盖率 **1.00**：三块里事实点全中，却因为绝对分低被判成「不相关」。

于是「零误拒」的阈值只有一个：**0.00**，也就是把门禁关掉。

## 4. 为什么分数不可信（机制层面）

`bge-reranker-base` 输出的是**这一对（问题，片段）像不像**，不是**这段文字有没有答案**：

- 片段是长表格、或答案落在 256 token 截断点之后 → 分数崩到 0.02（熔断那题）；
- 片段与问题用词高度重合、但答的是另一件事 → 分数 0.97（监控那题，三个片段全是
  指标表的三行，事实点在告警表）。

这不是阈值没调好，是**信号本身测的不是这件事**。换相对判据（top1 与 top2 的差值、
比值）也一样不成立：

| 判据 | 失败题取值 | 正常题取值 | 可分？ |
|---|---|---|---|
| top1 | 0.120 / 0.705 / 0.775 / 0.970 | 0.019 ～ 0.995 | ❌ 完全重叠 |
| top1 − top2 | 0.001 / 0.111 / 0.213 / 0.627 | 0.003 ～ 0.976 | ❌ 完全重叠 |
| top1 / top2 | 1.00 / 1.43 / 5.26 / 13.95 | 1.00 ～ 77.9 | ❌ 完全重叠 |

（「监控哪些指标」三块分数是 0.970 / 0.969 / 0.968 —— 又平又高，是「同表挤占」的
典型形状；而「系统组成部分」0.120 / 0.009 / 0.001 又尖又低，却同样没答到。）
**平坦与陡峭、高与低，在两类题里都出现。**

## 5. 那落地了什么

不做阈值改动，做**让拒答可核对**。门禁清空上下文时这条路径此前完全静默：
用户看到「知识库里没有找到」，而运维侧查不到任何记录，也就永远无法回答
「线上到底拒了多少、拒掉的是不是本该能答的」。

新增日志 `pipeline.kb.relevance_gate_suppressed`（REPORTABLE），每次拒答带齐：

| 字段 | 用途 |
|---|---|
| `threshold` | 当时用的阈值（改配置后能对上账） |
| `max_score` / `avg_score` | 差多少；两者一起看才知道是「全低」还是「均值拖累」 |
| `gap_to_threshold` | 离阈值多远——0.29 vs 0.02 是完全不同的两种情况 |
| `chunks` | 丢掉了几块 |
| `top1_preview` | 被丢掉的那块开头 80 字（单行），事后一眼能看出「这题本该能答」 |

有了它，下一次动阈值的依据是**生产真实拒答样本**（人工判「这题该不该拒」），
而不是 24 道构造题。

## 6. 与之前结论的关系

- 2026-11-10 白天我建议「优先做低置信兜底」——**这份数据把它推翻了**，
  和「加宽窗口」「章节去重」一样，属于先验证再否掉的第三种修法；
- 泛问的 4 道失败**不是**置信度问题，是内容层面的：重排对表格行/长块打分失真、
  术语缺口（问「换模型」、文档写 `embedding_migration`）；
- 因此下一步仍回到结构改动：**表格感知选择**（同表只占一席 + 选中后整表回填），
  它要改的是「选什么」，不是「信不信」。

## 7. 边界

- 24 题、1 题 = 4.2pp；0.15 与 0.30 的差别是**1 道题**，不足以据此改生产默认值；
- 「该拒」的标注是**代理指标**（三块拼起来没答到任何事实点），不是人工判定的
  「这题知识库里没有」——两者可能不一致（覆盖率 0 也可能只是没答全）；
- 结论只在这份语料（4 篇项目文档、606 块）与这个重排模型上成立；
  换模型或换语料需要重跑本评估。

## 8. 复现

```bash
python backend/scripts/eval_relevance_gate.py --probe backend/data/probe-prod-20261110.json
python backend/scripts/eval_relevance_gate.py --probe docs/benchmarks/stage-probe-2026-11-10.json
python backend/scripts/eval_relevance_gate.py --probe <报告> --check 0.15   # 单点判定，有误拒则 exit 1
```
