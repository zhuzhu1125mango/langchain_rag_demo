# 表格感知选择的组合验证：三条只成立一条

> 2026-11-11。承接 [table-selection-2026-11-11.md](table-selection-2026-11-11.md) 的三级诊断。
> 上一轮证明「同表折叠」和「整表回填」单独做都是负收益，原因是**候选池里本来就没有货**。
> 本轮把「扩池 → 融合候选上折叠 → 放开窗口」三件事一起放开，看是否只有组合才有效。
>
> 结论：**只有「在融合候选上折叠」有效，另外两条是负的**，其中「扩池」不仅无效还有副作用。
> 而且这次改动在生产索引上验证过：24 题里只有 1 道覆盖率变化（就是目标题），
> 没有任何一题变差。

## 1. 先纠正一条前提：生产重排只排序，不筛选

`search_hybrid` 里：

```python
rerank_n = max(k, _ab_rerank_top_k())   # 线上 k=3、KB_HYBRID_RERANK_TOP_K=3 → rerank_n = 3
candidates = fused[:rerank_n]
reranked = await rerank_results(query, candidates, top_k=k)
```

**窗口等于最终块数**。这意味着在生产配置下，重排只能给这 3 条重新排个序，
**不能换人**。于是「哪 3 块进上下文」完全由 RRF 融合顺序决定。

这解释了两件此前反复出现的怪事：

- 为什么调重排窗口 3→5→20 一路变差（0.556→0.535→0.452）：窗口一旦超过 3，
  重排才开始真的参与筛选，而它筛得比 RRF 更差；
- 为什么所有「改选择规则」的做法都是负收益：选择发生在重排之后，
  而重排之后总共只有 3 条，没有选择空间。

所以本轮的折叠**必须**插在 RRF 之后、截断之前。

### 为什么扩池无效

三级诊断时写过「告警行 BM25 名次 20 / 64 / 51，结构上进不了池子」。本轮把每个事实点
摊开看，实际是：

| 事实点 | BM25 名次 | 融合名次 |
|---|---|---|
| `ScrapeTargetDown`（池里唯一有的那个） | **20** | **13** |
| `PostgresDatabaseDown` | 64 | 更后 |
| 处置速查 | 51 | 更后 |

池子 20 已经把**能捞到的那一个**捞进来了（名次 13）。扩到 64 只是把另外两个事实点
和一堆噪声一起放进来，而融合是名次的函数，前面 20 条的顺序不变 —— 噪声在后面
稀释不了它们，反而在折叠后改变了名额分配。

实测代价：「生产环境升级换版本要注意什么」从 0.50 掉到 **0.00**
（`deployment#45` 的 `SIGTERM` 被 `backup-restore#37` 挤掉）。扩池 3 个数量级、
零收益、一道题变差，直接排除。

### 为什么放开窗口有害

折叠后目标题候选从 25 条压到 7 条，窗口 20 等于把 7 条全送重排。重排给出的前 3 是：

| 重排分 | 块 | 内容性质 |
|---|---|---|
| 0.9700 | `deployment.md#227` | 7.3 监控指标（另一张指标表） |
| 0.9247 | `monitoring.md#11` | 3. 核心业务指标（又一张指标表） |
| 0.8146 | `monitoring.md#0` | **文档元信息块**（标题 + 定位 + 配置路径 + 更新时间） |
| 0.7884 | `monitoring.md#32` | ✅ 4. 告警规则 ScrapeTargetDown |

正确答案排第 4。窗口 3 时它刚好进（窗口里就 3 条，全进）；窗口 20 时它被挤出。
**重排偏爱「字面相似但无答案」的块**——标题块、指标表行都比告警行更像这个问题。

这也解释了「去元信息块」为什么没有额外收益：去掉 `monitoring#0` 后顶上来的
`monitoring#11` 仍然是另一张指标表，覆盖不变。真正缺的不是过滤规则，是候选质量。

## 3. 生产索引验证（不动线上配置）

新增开关 `KB_TABLE_FOLD_ENABLED`（默认 **false**，线上行为零改变），
用 `probe_prod_stages.py --fold-table` 在生产 Milvus 的 606 块上跑同一批 24 题：

| 指标 | 关闭 | 开启 |
|---|---|---|
| 概览(12) | 0.556 | **0.597** |
| 细节(12) | 0.792 | 0.792 |
| 邻块回填后 概览 | 0.597 | **0.681** |
| 候选池覆盖率 概览 / 细节 | 0.792 / 1.000 | 0.771 / 0.917 |
| 答案在融合 top10 内 概览 / 细节 | 10/12 · 11/12 | 11/12 · 11/12 |

逐题只有 3 题换了选中的块，其中**只有 1 题覆盖率变化**：

| 题 | 关闭 | 开启 |
|---|---|---|
| 监控哪些指标、有哪些告警？ | 0.00（`#227` / `#231` / `#230`，同表三行） | **0.50**（`#227` / 元信息块 / `#32` 告警行） |
| 容量怎么规划，什么时候该扩容？ | 0.50 | 0.50（换块，事实点仍命中） |
| 备份和恢复的 RPO / RTO 目标是多少？ | 1.00 | 1.00（换块，事实点仍命中） |
| 其余 21 题 | — | 完全不变 |

**没有任何一题变差，包括细节题。** 折叠的规模：融合候选平均 32.1 → 23.0
（删 9.2 条，23/24 题有删除），折叠后最少的题仍剩 7 条，24/24 题都 ≥ 3，不会出现返回不足。

一个额外的观察：折叠后**邻块回填的收益变大**了（概览 0.597 → 0.681，vs 基线 +12.5pp，
不折叠时只有 +4.1pp）。这两个动作可能互补——但邻块回填本身还没上生产，
属于另一笔账，本轮不并入。

## 4. 落地

- `backend/src/services/table_chunks.py`：`table_header_of` + `fold_same_table_rows`，
  判据与离线探针一致（只认「表头 + 一行」形态，不碰整表块和普通段落）
- `milvus_search.search_hybrid`：RRF 之后、`fused[:rerank_n]` 之前折叠，受开关控制，
  `timings["table_fold_removed"]` 记录删了几条
- `KB_TABLE_FOLD_ENABLED`：默认 **false**
- `tests/test_table_fold.py` 13 例：行级块识别、整表块不折叠、不同文档同表头不合并、
  顺序保持、入参不变、默认关闭

## 5. 为什么不默认打开

收益是 **+4.1pp（约半道题）**，样本是 24 题，1 题 = 4.2pp。虽然四份独立数据
（本地 614 块 / 生产 606 块 / 开关两态 / 邻块回填）方向一致且无负例，
但这个量级仍不足以支撑「默认改变线上检索结果」的决策。

打开它的正确时机是：先用它跑一段时间观测（`table_fold_removed` 已在 timings 里），
或者等评测集扩到 ~40 题后再判一次。**现在默认关，是"已实现、已验证、待决策"的状态，
不是"已上线"。**

## 6. 未测

- **多查询路径**（`search_hybrid_multi`）没有接入折叠。该路径默认关闭，且离线 A/B 无增益。
- **折叠后不足 k 块**的极端情况没有真实样本（最小剩余 7）。若某篇文档几乎全是同一张表的行，
  折叠后可能返回少于 k 条。当前不兜底——退回未折叠会把折叠掉的行又加回来，等于关掉机制。
- **真实流量**上的效果未测：生产 24 题都是项目文档题，而真实提问六成在问产品型号
  （知识库里没有这类文档，见 [trace-inventory-2026-11-10.md](trace-inventory-2026-11-10.md)）。
