## 1. 为什么要做这个对比

此前项目里「混合检索更好」「加个重排更准」都只有配置与直觉，没有数字。
上一份[检索基线](retrieval-baseline-2026-11-02.md)只测了 BM25 一条腿，结论是
「制度问法 40/40 全中、口语化只有 9/20」——那自然会问：另一条腿能补多少？融合与重排各自贡献多少？

## 2. 方法

| 项 | 内容 |
|---|---|
| 数据集 | 同一份 `kb_eval_dataset.jsonl`（70 题：40 policy / 20 colloquial / 4 multi_hop / 6 no_answer） |
| 语料 | 同一份 `eval_corpus.jsonl`（72 篇，含 12 篇近义干扰） |
| 粒度 | 文档级，最终截断 K = 5（与 CI 卡点口径一致） |
| 通道候选 | 各通道先取 Top-**20** 再融合（与生产 `KB_HYBRID_SEARCH_TOP_K=20` 一致） |
| sparse | BM25 + jieba（与生产同一套） |
| dense | Ollama `bge-m3:latest`，余弦相似度（与生产同一模型） |
| 融合 | RRF，k = 60（与生产 `KB_RRF_K=60` 一致） |
| 重排 | `BAAI/bge-reranker-base` / `BAAI/bge-reranker-v2-m3`，`max_length=256`，**CPU** |

## 4. 三条能站得住的结论

### ① 差距全在口语化，制度题四条通道都是满分

40 道制度问法在**任何**通道下都 100% 命中——这说明在这个语料上「检索难」不是词表覆盖问题，
而是**用户表达与文档用词之间的距离**。稀疏 9/20、稠密 17/20，差的这 8 道题就是一切优化该瞄准的地方。

### ② RRF 等权融合会把稠密的优势稀释掉：17 → 13

RRF 只看**排名**、不看分数，所以一个在稀疏通道排第 1、在稠密通道排第 30 的文档，
融合后仍然靠前。口语化问题恰好是稀疏通道最不靠谱的场景（它排第 1 的那篇往往是错的关键词命中），
于是一篇错文档被两路「共同认可」顶上来，把稠密已经排对的正确文档挤下去。

**改进方向不是加大候选，而是给通道加权**（例如 sparse 权重 0.3 / dense 1.0），或改成按分数归一化融合。
这份报告只证明了「等权 RRF 有代价」，没证明哪种加权最好——那需要另一轮实验。

### ③ 生产配的 base 重排是负收益，换 v2-m3 才转正

- `dense + rerank-base`：0.922，比不重排的 `dense`（0.953）**低 2 道题**——
  重排把稠密已经排对的题又压了下去；
- `dense + rerank-v2`：0.969（18/20 口语题），比 base 高 3 道题，是全局最高；
- 但 v2 的 **MRR 反而略降**（0.892 vs 0.906）：把漏掉的捞回来了一些，代价是部分本来排第 1 的被挪后。

结论很具体：**重排不是「开了就更好」的开关，模型选型与截断长度会决定正负号**。

`并集 + rerank` 与前两者完全同分也说明一件事：**瓶颈不在候选池，而在打分与排序**。

## 5. 延迟：不能只看准确率

CPU 上 20 候选 × 70 题的重排耗时：

| 模型 | 总耗时 | 折合每题 |
|---|---|---|
| `bge-reranker-base` | 86s | ≈1.2s |
| `bge-reranker-v2-m3` | 365s | ≈5.2s |

5 秒/题在交互式问答里不可接受。所以「换 v2-m3」不是一个纯收益的动作：
要么上 GPU，要么减候选数，要么只在长文档/低置信场景启用。**这条数字比准确率更能决定是否真的能上线。**

## 6. 这份结论的边界（重要）

1. **文档级、短文档**：语料每篇 110~200 字；生产是按 ~512 字 chunk 召回，同一文档会有多个块，
   稀疏通道的相对表现可能不同；
2. **语料规模小（72 篇）**：稠密在候选池小时占便宜；真实知识库上千块时，稀疏的精确术语匹配价值会上升；
3. **合成语料**：制度文档表述规整，真实文档的口语化与噪声更多；
4. **单次测量、无置信区间**：20 道口语题下，1 道题 = 5pp；跨 3~4 道题的差异才值得当成信号；
5. **RRF 的 k 与通道权重没调**：本报告固定 k=60（生产值），没有搜索最优；
6. **重排在 CPU 上跑**：GPU 上延迟结论会完全不同。

## 7. 复现

```bash
cd backend
# 需要本机 Ollama 已 pull bge-m3（首次会写缓存到 backend/data/cache/eval_embeddings）
uv run python scripts/run_channel_ab.py --arms sparse,dense,hybrid,rerank --report /tmp/ab.json
uv run python scripts/run_channel_ab.py --arms dense,dense_rerank \
  --rerank-model BAAI/bge-reranker-v2-m3 --report /tmp/ab-v2.json
uv run python scripts/run_channel_ab.py --arms sparse                # 无 Ollama 也能跑
```

脚本**不进 CI**：它依赖本机 Ollama 与 1~2GB 重排模型；CI 卡点仍是纯离线的 `run_eval.py`。

## 8. 下一步（按证据强度排序）

1. **在真实 chunk 语料上重跑**：把 72 篇按 `CHUNK_SIZE=512` 切块（约 200~300 块）再测一次，
   看「稠密 > 混合」是否依然成立——这是唯一能推翻或确认本报告的条件；
2. **加权 RRF 实验**：sparse 权重扫 0.2/0.3/0.5，看口语子集能否补回那 4 道题；
