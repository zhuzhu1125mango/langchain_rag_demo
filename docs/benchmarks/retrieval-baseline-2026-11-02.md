# 检索基线报告 · 2026-11-02

> 一句话：**稀疏通道（BM25）在 72 篇语料、64 道有答案题上 hit_rate@5 = 0.828、MRR@5 = 0.775**；
> 11 道失分**全部是口语化提问**，制度型问题 40/40 全中。这个数字不是产品效果，是**检索回归的地板**——
> 它只测「能不能把对的那篇捞进前 5」，不测生成的答案对不对。

## 1. 为什么做这个

此前评测集只有 **5 道题、12 篇语料**，hit_rate 恒为 1.0：任何改动都不会让它动，等于没有指标。
本报告把这层补上：数据集扩到 **70 题 / 72 篇**，并在 CI 里做卡点。

一天之内改过两次规模，顺序本身说明为什么最后是这个数：

| 版本 | 规模 | hit@5 | 为什么又改 |
|---|---|---|---|
| 原始 | 5 题 / 12 篇 | 1.000 | 没有区分度 |
| 第一版扩容 | 58 题 / 72 篇 | 0.904 | 口语化题只有 8 道，1 道题=12.5pp，通道对比没有统计意义 |
| **本报告** | **70 题 / 72 篇** | **0.828** | 口语化题补到 20 道后，稀疏通道的真实短板才暴露出来 |

## 2. 方法

| 项 | 内容 |
|---|---|
| 数据 | `backend/tests/evaluation/kb_eval_dataset.jsonl`（70 题）、`eval_corpus.jsonl`（72 篇） |
| 检索栈 | 与生产同一套中文 BM25：`pymilvus.model.sparse.BM25EmbeddingFunction` + jieba 分析器 |
| 粒度 | 文档级：一题取 Top-5，命中任一 golden 文档即算 HIT |
| 指标 | `hit_rate@5`（有没有捞到）、`MRR@5`（捞到得多靠前）、`recall@5`（多跳题两篇捞到几篇） |
| 无答案题 | 6 道（班车/年会抽奖/健身房/期权/食堂菜单/宠物），只统计 top1 分数分布，**不并入上面三项** |

题目构成（70 道）：

| 类型 | 数量 | 说明 |
|---|---|---|
| policy | 40 | 照着制度条目问，与语料用词接近 |
| colloquial | 20 | 口语化（「出去玩几天」而不是「请假」、「想换个座位」而不是「工位」） |
| multi_hop | 4 | golden 两篇（如「住宿超标谁审批 + 标准在哪查」） |
| no_answer | 6 | 语料里确实没有，用于观察分数通道能否区分 |

语料 72 篇：12 篇原始 + 48 篇制度文档（财务/研发/数据合规/客服/运维/人事/行政）+ **12 篇近义干扰**
（旧版已废止制度、境外差旅、日常报销、弹性考勤、分级草案、热修复、服务账号密码、企业退款…）。
干扰篇是故意加的：真实知识库里最难的从来不是近义词，而是**同一主题的多个版本/多个场景**。

## 3. 结果

```
hit_rate@5 = 0.828    mrr@5 = 0.775    recall@5 = 0.828
有答案 64 题 / 无答案 6 题 / 语料 72 篇
单题排序耗时 p50 = 0.27ms  p95 = 0.95ms（纯本地 BM25 打分，不含向量库/网络/LLM）
```

按题型拆开，结论比总分清楚得多：

| 子集 | 题数 | 命中 | 平均 MRR |
|---|---|---|---|
| 制度问法（policy） | 40 | **40（100%）** | 0.94 |
| 口语化（colloquial） | 20 | **9（45%）** | 0.48 |
| 多跳（multi_hop） | 4 | 4（100%） | 0.875 |

> 40/40 与 9/20 的对比就是这份报告的价值：**在「知道该查什么词」的前提下，BM25 已经够了；
> 用户的真实问法才是瓶颈。** 这也解释了为什么加 dense 通道不是「换一个更高级的模型」，
> 而是补一个结构性缺口——见 [channel-ab-2026-11-02.md](channel-ab-2026-11-02.md)。

**失分的 11 道（全部是口语化题）**：

| 问题 | 期望 | 实际 Top-2 |
|---|---|---|
| 我想出去玩几天，流程上要提前多久跟领导说？ | leave_policy | fin_budget_adjust / reimbursement |
| 自己先垫钱买的东西，怎么把钱拿回来？ | reimbursement | rd_rollback / ops_wifi |
| 在家干活要连什么东西才能进公司系统？ | remote_work | ops_password / meeting_policy |
| 年底发的那笔钱是怎么算出来的？ | bonus_policy | adm_team_building / adm_parking_ev |
| 刚进来头几个月算正式员工吗？ | hr_probation | rd_api_version / sec_data_class_draft |
| 想换个座位找谁？ | adm_seat | adm_parking_ev / ops_password_service |
| 部门聚餐的钱怎么报？ | adm_team_building | fin_petty_cash / adm_parking |
| 半夜系统报警谁爬起来处理？ | rd_oncall | ops_password / adm_visitor |
| 发版出问题怎么退回去？ | rd_rollback | adm_parking_ev / ops_password_service |
| 买台新电脑要走什么流程？ | it_equipment | hr_onboarding / fin_petty_cash |
| 想升职要满足什么条件？ | hr_promotion | rd_requirement_review / cs_refund |

失败原因一致：**问题里几乎没有能命中文档的实词**。BM25 只看词面，用户说「出去玩」，文档写「请假」。

## 4. 无答案题：分数能不能代替拒答

```
top1 分数中位数：有答案 11.84 / 无答案 3.05 → 分离度 0.26
```

分离度 0.26 意味着无答案题的 top1 分数大约是有答案题的 1/4。看起来能设个阈值拒答，但**不能**：

- 无答案题里「公司是否提供上下班通勤班车？」的 top1 并不低，而有答案题里也有分数不高的；
- BM25 分数不归一，语料一扩充、文档一增长，绝对分数就整体漂移，阈值会失效；
- 真正该拒答的判断在生成层（「检索到的内容是否足以回答」），检索分数只是它的输入之一。

所以这项只报告、不卡点。想让它变成可卡点的指标，前提是先有归一化分数或端到端的拒答评测。

## 5. 复现

```bash
cd backend
uv run python scripts/run_eval.py --report docs/benchmarks/retrieval-baseline-2026-11-02.json
uv run python scripts/run_eval.py --show-misses        # 只看没命中的题
```

CI 里由 `rag-eval` job 执行同一条命令；低于阈值直接失败：

| 阈值 | 默认 | 基线 | 说明 |
|---|---|---|---|
| `EVAL_MIN_HIT_RATE` | 0.80 | 0.828 | 留约 3pp（≈2 题）回退空间 |
| `EVAL_MIN_MRR` | 0.75 | 0.775 | 同上 |
| `EVAL_MIN_RECALL` | 0.80 | 0.828 | 同上 |

**调整顺序**：改数据集 → 重跑 → 在本目录留一份带日期的报告 → 再改阈值。
反过来（先调阈值让 CI 变绿）就是把指标变成装饰。

## 6. 这份基线的边界（别过度解读）

1. **只测检索，不测答案**：不涉及 LLM 生成、引用准确率、拒答质量；
2. **文档级、非 chunk 级**：生产按 chunk 召回再拼接，chunk 级评测（同一文档内多主题）尚未做；
3. **语料是合成的制度文档**：结构规整、表述一致，比真实企业文档「干净」；
4. **只覆盖 sparse 通道**：同数据集上 dense / hybrid / rerank 的对比见 [channel-ab](channel-ab-2026-11-02.md)；
5. **p95 不可当端到端延迟**：0.95ms 只是本地打分，不含 embedding、Milvus 往返与网络。

## 7. 下一步

1. **chunk 级评测**：把 72 篇按生产 `CHUNK_SIZE=512` 切块，看同文档内多主题时是否捞错块；
2. **拒答评测**：构造 20 道无答案题，端到端看模型是否承认「知识库没有」，而不是靠分数阈值假装；
3. 通道对比的结论（dense > hybrid > sparse）只在这份语料上成立，需要在真实 chunk 语料上复核。
