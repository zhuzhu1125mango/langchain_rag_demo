# 检索基线报告 · 2026-11-02

> 一句话：**稀疏通道（BM25）在 72 篇语料、52 道有答案题上 hit_rate@5 = 0.904、MRR@5 = 0.854**；
> 失分的 5 道全是「口语化提问」，不是制度类问法。这个数字不是产品效果，是**检索回归的地板**——
> 它只测「能不能把对的那篇捞进前 5」，不测生成的答案对不对。

## 1. 为什么做这个

此前评测集只有 **5 道题、12 篇语料**，hit_rate 恒为 1.0：任何改动都不会让它动，等于没有指标。
本报告把这层补上：数据集扩到 **58 题 / 72 篇**，并在 CI 里做卡点。

## 2. 方法

| 项 | 内容 |
|---|---|
| 数据 | `backend/tests/evaluation/kb_eval_dataset.jsonl`（58 题）、`eval_corpus.jsonl`（72 篇） |
| 检索栈 | 与生产同一套中文 BM25：`pymilvus.model.sparse.BM25EmbeddingFunction` + jieba 分析器 |
| 粒度 | 文档级：一题取 Top-5，命中任一 golden 文档即算 HIT |
| 指标 | `hit_rate@5`（有没有捞到）、`MRR@5`（捞到得多靠前）、`recall@5`（多跳题两篇捞到几篇） |
| 无答案题 | 6 道（班车/年会抽奖/健身房/期权/食堂菜单/宠物），只统计 top1 分数分布，**不并入上面三项** |

题目构成（58 道）：

| 类型 | 数量 | 说明 |
|---|---|---|
| 单跳·制度问法 | 43 | 与语料用词接近，代表「知道自己要查什么」的用户 |
| 单跳·口语问法 | 8 | 刻意不与原文共用关键词（「出去玩几天」而不是「请假」） |
| 多跳 | 4 | golden 两篇（如「住宿超标谁审批 + 标准在哪查」） |
| 无答案 | 6 | 语料里确实没有，用于观察分数通道能否区分 |

语料 72 篇：12 篇原始 + 48 篇制度文档（财务/研发/数据合规/客服/运维/人事/行政）+ **12 篇近义干扰**
（旧版已废止制度、境外差旅、日常报销、弹性考勤、分级草案、热修复、服务账号密码、企业退款…）。
干扰篇是故意加的：真实知识库里最难的从来不是同义词，而是**同一主题的多个版本/多个场景**。

## 3. 结果

```
hit_rate@5 = 0.904    mrr@5 = 0.854    recall@5 = 0.904
有答案 52 题 / 无答案 6 题 / 语料 72 篇
单题排序耗时 p50 = 0.24ms  p95 = 0.45ms（纯本地 BM25 打分，不含向量库/网络/LLM）
```

分项：

| 子集 | 题数 | 命中 | 平均 MRR |
|---|---|---|---|
| 单跳（含口语） | 48 | 43（89.6%） | 0.852 |
| 多跳（golden 2 篇） | 4 | 4（100%） | 0.875 |

**失分的 5 道（全部是口语问法）**：

| 问题 | 期望 | 实际 Top-3 |
|---|---|---|
| 我想出去玩几天，流程上要提前多久跟领导说？ | leave_policy | fin_budget_adjust / reimbursement / rd_requirement_review |
| 自己先垫钱买的东西，怎么把钱拿回来？ | reimbursement | rd_rollback / ops_wifi / fin_procurement |
| 在家干活要连什么东西才能进公司系统？ | remote_work | ops_password / meeting_policy / attendance |
| 年底发的那笔钱是怎么算出来的？ | bonus_policy | adm_team_building / adm_parking_ev / rd_release_hotfix |
| 刚进来头几个月算正式员工吗？ | hr_probation | rd_api_version / sec_data_class_draft / bonus_policy |

失败原因是一致的：**问题里几乎没有能命中文档的实词**。BM25 只看词面，用户说「出去玩」，
文档写「请假」；中间缺的正是 embedding 与改写要补的那一段。

结论不是「检索不行」，而是：**纯稀疏通道对口语化提问的召回约 90%；关掉 dense 通道会让召回直掉近 10 个百分点。**
生产链路是 hybrid（dense + sparse + rerank），这份基线只覆盖其中一条腿——这是它的价值（能定位是哪条腿退化了），
也是它的边界（不能拿它当端到端效果）。

## 4. 无答案题：分数能不能代替拒答

```
top1 分数中位数：有答案 12.72 / 无答案 3.05 → 分离度 0.24
```

分离度 0.24 意味着无答案题的 top1 分数大约只有有答案题的 1/4。看起来能设个阈值拒答，但**不能**：

- 无答案题里「公司是否提供上下班通勤班车？」的 top1 是 4.13，而有答案题里也有分数不高的；
- BM25 分数不归一，语料一扩充、文档一增长，绝对分数就整体漂移，阈值会失效；
- 真正该拒答的判断在生成层（「检索到的内容是否足以回答」），检索分数只是它的输入之一。

所以这项只报告、不卡点。想让它变成可卡点的指标，前提是先有归一化分数或端到端的拒答评测。

## 5. 复现

```bash
cd backend
uv run python scripts/run_eval.py --report docs/benchmarks/retrieval-baseline-2026-11-02.json
# 只看没命中的题：
uv run python scripts/run_eval.py --show-misses
```

CI 里由 `rag-eval` job 执行同一条命令；低于阈值直接失败：

| 阈值 | 默认 | 基线 | 说明 |
|---|---|---|---|
| `EVAL_MIN_HIT_RATE` | 0.85 | 0.904 | 留约 5pp 回退空间 |
| `EVAL_MIN_MRR` | 0.80 | 0.854 | 同上 |
| `EVAL_MIN_RECALL` | 0.85 | 0.904 | 同上 |

**调整顺序**：改数据集 → 重跑 → 在本目录留一份带日期的报告 → 再改阈值。
反过来（先调阈值让 CI 变绿）就是把指标变成装饰。

## 6. 这份基线的边界（别过度解读）

1. **只测检索，不测答案**：不涉及 LLM 生成、引用准确率、拒答质量；
2. **文档级、非 chunk 级**：生产按 chunk 召回再拼接，chunk 级评测（同一文档内多主题）尚未做；
3. **语料是合成的制度文档**：结构规整、表述一致，比真实企业文档「干净」；
4. **不含 dense / rerank**：这两条腿的效果需要另一份 A/B 报告（`scripts/run_multiquery_ab.py` 已有类似设施）；
5. **p95 不可当端到端延迟**：0.45ms 只是本地打分，不含 embedding、Milvus 往返与网络。

## 7. 下一步（按收益排序）

1. **chunk 级评测**：把 72 篇按生产 `CHUNK_SIZE=512` 切块，看同文档内多主题时是否捞错块；
2. **hybrid 前后对比**：同一数据集跑「sparse only / hybrid / hybrid+rerank」，给出各通道增量——这是向别人解释「为什么要 dense」的唯一硬证据；
3. **拒答评测**：构造 20 道无答案题，端到端看模型是否承认「知识库没有」，而不是靠分数阈值假装。
