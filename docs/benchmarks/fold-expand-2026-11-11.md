# 折叠 + 邻块回填：互补，不是叠加

> 2026-11-11 傍晚。承接 [table-combo-2026-11-11.md](table-combo-2026-11-11.md)。
> 上一轮发现折叠后「邻块回填」的收益从 +4.1pp 升到 +12.5pp，本轮验证这两件事
> 到底是互补还是重复，并把成本量出来。
>
> 结论：**互补**。邻块回填**单独用对目标题完全无效**（0.00 → 0.00），只有先折叠、
> 让正确的表进入窗口后，回填才能把它补全（0.50 → 1.00）。成本是上下文 2.8 倍字符，
> 但实测 prefill 只多约 200ms。

## 1. 四格对照（生产 606 块，24 题，窗口 3）

| 配置 | 概览(12) | 细节(12) | 概览字符 | 细节字符 | 平均块数 |
|---|---|---|---|---|---|
| 不折叠 / 不回填 | 0.556 | 0.792 | 732 | 923 | 3.0 |
| 不折叠 / 回填 | 0.597 | 0.833 | 1942 | 2460 | 7.9 |
| 折叠 / 不回填 | 0.597 | 0.792 | 793 | 969 | 3.0 |
| **折叠 / 回填** | **0.681** | **0.833** | 2028 | 2498 | 8.0 |

相对基线：折叠单独 +4.1pp，回填单独 +4.1pp，两者一起 **+12.5pp**（概览）。
1 + 1 > 2，说明它们作用在不同位置。

## 2. 为什么是互补：逐题看

| 题 | 不折叠 回填前→后 | 折叠 回填前→后 |
|---|---|---|
| 系统由哪些部分组成，请求怎么流转？ | 0.00 → 0.25 | 0.00 → 0.25 |
| 优雅停机怎么做？为什么需要？ | 0.50 → 0.75 | 0.50 → 0.75 |
| **监控哪些指标、有哪些告警？** | **0.00 → 0.00** | **0.50 → 1.00** |
| 为什么要给 NLTK 语料单独放进镜像？ | 0.50 → 1.00 | 0.50 → 1.00 |

关键在第三行：不折叠时，3 个名额全被同一张指标表的三行占满，**邻块当然也是指标表行**，
回填再多也只是把同一张表补得更全 —— 覆盖一动不动。折叠把名额换成「指标表 1 行 +
告警表 1 行」之后，回填才补到告警表的其余行和处置速查，直接到 1.00。

另外三题不受折叠影响（回填增量完全一致），说明回填本身是稳定的，不依赖候选怎么选。

## 3. 预算扫描：付多少最划算

无预算是 8 块 / 2028 字符。逐档压：

| 预算（字符） | 不折叠 概览 / 字符 / 块 | 折叠 概览 / 字符 / 块 |
|---|---|---|
| 900 | 0.556 / 939 / 4.2 | 0.597 / 940 / 3.8 |
| 1200 | 0.556 / 1123 / 5.1 | **0.639** / 1143 / 5.0 |
| 1600 | 0.556 / 1451 / 5.9 | 0.639 / 1512 / 6.0 |
| 2000 | 0.597 / 1688 / 7.2 | **0.681** / 1761 / 7.3 |
| 2600 | 0.597 / 1888 / 7.8 | 0.681 / 1974 / 7.8 |
| 无上限 | 0.597 / 1942 / 7.9 | 0.681 / 2028 / 8.0 |

两个拐点：

- **1200 字符拿到 0.639**（+8.3pp，比基线多 350 字符、多 2 块）——性价比最高；
- **2000 字符拿到 0.681**（+12.5pp，多 968 字符、多 4.3 块）——多花 618 字符换 4.2pp。

同一个预算下，折叠版永远优于不折叠版（1200：0.639 vs 0.556；2000：0.681 vs 0.597），
并且折叠版只用 3.8 块就能到 0.597（不折叠要 4.2 块）。**折叠省下的名额可以换成邻居。**

## 4. 成本实测：prefill 只多约 200ms

用生产同一个模型（`qwen3:4b`，`num_ctx=6144`）走 Ollama `/api/generate`，
拿真实语料拼不同长度的上下文，读 `prompt_eval_duration`：

| 上下文字符 | prompt tokens | prefill |
|---|---|---|
| 1200 | 693 | 196 ms |
| 2000 | 1129 | 333 ms |
| 3000 | 1607 | 350 ms |
| 5000 | 2678 | 890 ms |

（第一次 800 字符的 9.3s 是模型冷加载，已剔除。）

从 793 → 2028 字符约 +150～200ms prefill。相对端到端回答（生成主导，秒级）
可以忽略。**成本不是这条改动的阻碍。**

## 5. 但覆盖率测不出噪声

上面所有数字都是「事实点覆盖率」，它只回答「该有的有没有」，不回答
「多塞进来的有没有害」。回填的 5 个邻块里，必然有与问题无关的内容（章节过渡句、
相邻但不同主题的表格行）。这份数据**测不到**它们会不会让模型分心。

这一条是这条改动唯一没有被验证的地方，也决定了它不能仅凭 24 题的数字上线。

## 6. 建议

1. **实现顺序：先回填，后折叠。** 折叠已有开关（`KB_TABLE_FOLD_ENABLED`，默认关），
   回填尚未实现。若只做一件，做回填：+4.1pp 概览 / +4.1pp 细节，且不依赖其他改动。
2. **回填带 1200～2000 字符预算**，不要无上限。1200 是性价比拐点，2000 是收益拐点。
3. **两者都开才是完整形态**（0.681）。但先单独上回填、观察一轮，再叠折叠——
   一次改一件事，出问题能归因。
4. **实现代价**：`search_hybrid` 返回后按 `(document_id, chunk_index±1)` 批量补查一次
   Milvus（一次 query，约 5～20ms），再按预算拼装。改动比折叠大（要碰上下文组装层），
   需要单测钉住「不跨文档、不超预算、顺序稳定」。

## 7. 未测

- **噪声代价**：见 §5，覆盖率看不见这个。要么接答级评测，要么用真实流量 A/B。
- **多查询路径**：`search_hybrid_multi` 未接入折叠，回填同样未涉及。
- **答级效果**：覆盖率 +12.5pp 不等于「答对率 +12.5pp」。历史上（11-09）出现过
  「检索指标好看、回答仍错」的情况，这条必须用答级评测验收。
