# 融合策略对比：RRF 到底错在哪，以及这份数据撑不住什么（2026-11-02）

> 上一份 [channel-ab-2026-11-02.md](channel-ab-2026-11-02.md) 得出「dense 单通道打赢生产默认的 hybrid+rerank」。
> 那份报告留了个问题没回答：**是融合这件事本身不行，还是 RRF 这个融合方式不行？**
> 这份报告回答它，并且——更重要的是——说明**哪些结论这份数据根本撑不住**。

## 0. 一句话结论

| 想说的 | 数据支持吗 |
|---|---|
| dense 明显强于纯 BM25 | ✅ **支持**：+14.06pp，9 题对 0 题，p = 0.0039 |
| 分数融合优于等权 RRF | ◐ **方向一致但未达显著**：三档权重合并 7:0（RRF 一题都没独赢），单组 p = 0.25 |
| 加权分数融合强于纯 dense | ❌ **不支持**：0.938 vs 0.922，只差 1 道题，p = 1.0000 |
| 换融合方式能让 hybrid 追上 dense | ❌ **不支持**：最好 0.938，与 dense 的 0.922 在噪声内 |

**这批数据只够支撑一条判断：dense 比 BM25 强。融合方式之间的差异全在噪声里。**

## 1. 为什么用 top-3 而不是 top-5

生产实际配置（`docker exec backend-prod` 读到的生效值）：

```
KB_ENABLE_HYBRID_SEARCH   = True
KB_HYBRID_SEARCH_TOP_K    = 20      # 每路召回 20
KB_HYBRID_RERANK_TOP_K    = 3       # ← 最终只给 LLM 3 条
KB_RRF_K                  = 60
KB_RERANK_ENABLED         = True
KB_RERANK_MODEL           = BAAI/bge-reranker-base
```

之前的通道对比用 top-5，与生产口径不符。K 从 5 收到 3 之后**排序完全没变**，
这本身是稳健性证据：

| arm | hit@5 | hit@3 | MRR@5 | MRR@3 | 口语@5 | 口语@3 |
|---|---|---|---|---|---|---|
| sparse | 0.828 | 0.781 | 0.775 | 0.766 | 0.45 | 0.30 |
| dense | **0.953** | **0.922** | 0.906 | 0.898 | 0.85 | 0.75 |
| hybrid (RRF k=60) | 0.891 | 0.859 | 0.820 | 0.812 | 0.65 | 0.55 |
| hybrid+rerank | 0.922 | 0.906 | 0.892 | 0.888 | 0.75 | 0.70 |
| dense+rerank | 0.922 | 0.906 | 0.892 | 0.888 | 0.75 | 0.70 |
| union+rerank | 0.922 | 0.906 | 0.892 | 0.888 | 0.75 | 0.70 |

当时没深究的细节：**三个重排臂的数字一模一样**（0.922 / 0.906）。不管喂给重排器的候选
来自 hybrid、dense 还是并集，重排后结果完全相同——`bge-reranker-base` 在这里是**能力上限**，
它把上游通道的差异彻底抹平，而自己那个上限还低于不重排的 dense。
重排不是「锦上添花」，是「统一降级」。

## 2. 融合策略：RRF vs 分数融合

RRF 只吃排名不吃分数：`score = Σ 1/(k+rank)`。第 1 名与第 10 名的差距被压成
`1/61` 与 `1/70`（差 13%），而两者的实际相似度可能差一倍。分数融合保留这部分信息。

（top-3，64 道有答案题；wrrf = 加权 RRF，sfuse = min-max 分数融合，数字为 dense 权重）

| arm | hit@3 | MRR | 口语(20) | 说明 |
|---|---|---|---|---|
| sparse | 0.781 | 0.766 | 0.300 | 单稀疏 |
| dense | 0.922 | 0.898 | 0.750 | 单稠密 |
| wrrf50 | 0.859 | 0.812 | 0.550 | **= 生产当前的等权 RRF** |
| sfuse50 | 0.875 | 0.857 | 0.600 | 同权重，只换融合方式 |
| wrrf70 | 0.875 | 0.833 | 0.600 | |
| sfuse70 | 0.922 | 0.891 | 0.750 | 追平 dense |
| wrrf85 | 0.891 | 0.865 | 0.650 | |
| **sfuse85** | **0.938** | **0.901** | **0.800** | 表内最高，但见 §3 |

三档权重下分数融合每次都赢 RRF，而且是 **7 : 0**——三个权重档位加起来，
**RRF 一题都没独赢**。方向一致性比数字本身更有说服力。

## 3. 显著性检验：这里必须泼冷水

64 道有答案题，**1 道题 = 1.56pp**。McNemar 精确检验（只统计不一致对，
两臂都中/都不中的题不携带信息）：

| 比较 | Δ | 不一致对 (A胜:B胜) | p 值 | 判读 |
|---|---|---|---|---|
| sparse → dense | +14.06pp | 0 : 9 | **0.0039** | ✅ 显著 |
| wrrf50 → sfuse50 | +1.56pp | 0 : 1 | 1.0000 | 噪声内 |
| wrrf70 → sfuse70 | +4.69pp | 0 : 3 | 0.2500 | 噪声内 |
| wrrf85 → sfuse85 | +4.69pp | 0 : 3 | 0.2500 | 噪声内 |
| dense → sfuse70 | 0.00pp | 1 : 1 | 1.0000 | 完全打平 |
| dense → sfuse85 | +1.56pp | 0 : 1 | 1.0000 | 噪声内 |

**只有第一行是真的。** 其余全部不能说。

注意 `dense → sfuse70` 是 1:1——两臂命中数相同，只是**换了一道题**。
这是「0.938 vs 0.922 谁更强」这类讨论最典型的结局：同一批数据里，两个方案的
命中集互换一两个元素，汇总数字就产生了 1.6pp 的差，然后被当成结论。

### 一个意外收获：调参在噪声里拟合

把归一化区间从 `[0, 1]` 改成 `[0.5, 1]`（原因见 §5），同一份数据、同一批题，
**最佳权重就从 0.7 漂到了 0.85**：

| | 归一化 [0,1] | 归一化 [0.5,1] |
|---|---|---|
| sfuse50 | 0.906 | 0.875 |
| sfuse70 | **0.938** ← 最佳 | 0.922 |
| sfuse85 | 0.922 | **0.938** ← 最佳 |

实现细节的一处调整就能让「最优参数」搬家。在 64 道题上做权重网格搜索，
找到的不是最优参数，是这份语料的随机波动。

### 需要多少题才够

达到 p < 0.05 的最低门槛是 **6 个同向不一致对**（6:0 时 p = 0.031；5:0 时 p = 0.0625）。
按各组观察到的不一致率反推所需题量：

| 要检测的效应 | 观察到的不一致率 | 需要题量（约） |
|---|---|---|
| 14pp（通道级：sparse vs dense） | 9/64 ≈ 14% | **43 题** ← 当前 64 题够用 |
| 4.7pp（融合方式：RRF vs sfuse） | 3/64 ≈ 4.7% | **128 题** |
| 1.6pp（同一通道的参数微调） | 1/64 ≈ 1.6% | **384 题** |

**方法学结论：评测集的规模必须匹配你要检测的效应量。**
64 题的集子比「通道」，结论可靠；用它比「融合策略」，测出来的排序有一半概率是掷硬币的结果。
公开材料里大量 A/B 结论互相打架，多数不是谁做错了，而是样本量与效应量不匹配。

## 4. 最终建议

**不要基于这份数据改生产配置。** 这条比上面所有数字都重要。

可以做的：

1. **保留 hybrid 是对的，但 RRF 值得换**。7:0 的方向证据足够支持「值得试」，
   不足以支持「已经证明更好」。想落地，先补评测集到 ≥130 道有答案题，再跑一次本报告，
   看 p 是否 < 0.05。
2. **不建议**为了 1.6pp 换成纯 dense——差异在噪声内，而放弃稀疏通道会让
   专有名词、编号、错误码这类精确匹配场景失去保障，而那些场景本评测集**根本没有覆盖**
   （语料是制度文档，没有型号与错误码）。
3. **重排问题比融合问题更实在**：三个重排臂收敛到同一数字，说明 `bge-reranker-base`
   是当前上限，且低于纯 dense。这条比「融合方式」更值得投入——但同样需要更大评测集才能定论。

## 5. 实现细节里的一个坑

分数融合要把 BM25（无上界，本例到 12.0）与余弦（[0,1]）放到同一尺度。做法是各自
min-max 归一化。第一版映射到 `[0, 1]`，测试直接抓到问题：

```
w=1.0 时（只用 dense），结果里却混进了 sparse 的第 1 名，把 dense 的第 3 名挤掉了
```

原因：每路的最低分归一化后都是 `0`，而「只出现在另一路」的文档在合并时也是 `0` 分，
两者并列，谁在前由**字典插入顺序**决定。改为映射到 `[0.5, 1]` 后消失——
语义上也更合理：进过候选池的文档，都优于没进过的。

这个 bug 只在权重取极值时显现，但同款并列在真实配置下（20 候选、top-3）也会发生在尾部截断处。

## 7. 边界

- **文档级指标**：只回答「捞对哪一篇」，不回答「拼进 prompt 的 3 条 chunk 里有几条有用」。
  当前语料每篇 100–200 字，`CHUNK_SIZE=512` 下切不出多个 chunk，chunk 级评测现在做不出来
  （硬做就得到「1 篇 = 1 块」的退化结果）。要做，先把语料写成真正的长文档。
- **语料是合成的**：72 篇制度文档，12 篇近义干扰是刻意构造的。真实知识库的干扰形态更多
  （编号、旧版、扫描件 OCR 噪声），结论迁移到生产需再验。
- **口语化题是刻意构造的**：20 道题特意不与原文共用关键词，为的是放大通道差异，
  这也意味着口语化子集的权重高于它在真实流量里的占比。
- **未覆盖精确匹配**：没有型号、错误码、合同编号类问题，而稀疏通道的价值恰恰在这些场景。
  这使本报告对「要不要保留 sparse」的结论**偏保守**（低估了 sparse 的价值）。
- **dense 走 Ollama `bge-m3:latest`**（与生产 `EMBEDDING_MODEL_NAME` 同源），
  但生产走 Milvus 索引 + 分块，本脚本是 numpy 全量余弦 + 整篇文档。检索算子的差异未验证。
