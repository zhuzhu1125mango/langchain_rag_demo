# 检索通道与融合策略：显著性检验（2026-11-02，90 题版）

> 这份报告只回答一个问题：
> **生产该用 hybrid + rerank，还是换成别的组合？**
>
> 上一版（70 题）得出「dense 单通道打赢 hybrid+rerank」。这一版把数据集补上了真实流量里
> 最重要的题型——「产品型号 + 字段」的精确匹配查询——然后所有数字重算。
> 结论比上一版**更窄**，而不是更宽。

## 0. 结论

| 想说的 | 数据支持吗 |
|---|---|
| dense 明显强于纯 BM25 | ✅ **显著**：+15.48pp，13 题对 0 题，p = 0.0002 |
| dense 强于 hybrid（RRF） | ⚠️ **不显著**：+5.95pp，6 题对 1 题，p = 0.125 |
| 分数融合优于 RRF | ◐ **方向一致但未达显著**：8:0 全同向，最好一组 p = 0.0625（差一题） |
| hybrid 加重排比不加重排好 | ⚠️ **不显著**：+3.57pp，4 题对 1 题，p = 0.375 |
| 换融合方式能超过 dense | ❌ **不支持**：sfuse85 0.952 vs dense 0.941，1 题之差，p = 1.0 |

**唯一站得住的判断仍然是「稠密通道强于稀疏通道」。
生产当前的 `hybrid + rerank` 与纯 dense 之间的差异，在统计上无法区分。**

所以：**不改生产配置**。不是因为它更好，而是因为**没有证据说它更差**——
没有证据时改动生产，风险大于收益。

## 1. 这一版补了什么，为什么必须补

翻生产 `request_traces` 的 82 条真实问题，分布是这样的：

| 类型 | 条数 | 例子 |
|---|---|---|
| **产品型号 + 字段** | **约 50** | 「智星 X1 有几个 USB 接口？」「智星 X1 通过了哪些认证？」 |
| 通用知识（无检索需求） | 约 15 | 「什么是向量数据库」「区块链用两三句话解释」 |
| 天气 / 闲聊 / 元问题 | 约 17 | 「北京今天天气怎么样」「我刚才问了你什么」 |

**六成流量在问同一台设备的参数**，而上一版评测集的 72 篇语料全是制度文档，
一篇产品手册都没有。这意味着上一版所有结论都建立在一个**与真实分布正交**的语料上。

补了 6 篇产品文档（X1 规格书 / X1 运维手册 / 保修政策 / 安装指南）与 **20 道题**，
题干**原样取自真实 traces**（「有几个 USB 接口」「产生 CPU 过载告警的条件是什么」）。
语料里刻意埋了 **X1 Pro 与 X2**：型号只差一个字符、数值全不同，这是两类通道最容易分道扬镳的地方。

数据集现在 **90 题 / 78 篇**：policy 40、colloquial 20、**exact_match 20**、multi_hop 4、no_answer 6。

## 2. 结果（top-3，生产口径；84 道有答案题）

| arm | hit@3 | MRR | 口语(20) | 精确匹配(20) | 制度(40) |
|---|---|---|---|---|---|
| sparse | 0.786 | 0.720 | 0.300 | **0.800** | 1.000 |
| dense | 0.941 | **0.905** | 0.750 | 1.000 | 1.000 |
| hybrid (RRF k=60) | 0.881 | 0.788 | 0.500 | 1.000 | 1.000 |
| wrrf70 | 0.881 | 0.825 | 0.500 | 1.000 | 1.000 |
| sfuse70 | 0.941 | 0.849 | 0.750 | 1.000 | 1.000 |
| wrrf85 | 0.917 | 0.863 | 0.650 | 1.000 | 1.000 |
| **sfuse85** | **0.952** | 0.895 | **0.800** | 1.000 | 1.000 |
| hybrid+rerank | 0.917 | 0.883 | 0.700 | 0.950 | 1.000 |

top-5 口径下排序不变（sparse 0.869 / hybrid 0.917 / dense 0.964），结论对 K 不敏感。

三个值得单独说的现象：

**① MRR 与 hit 会分家。** `sfuse70` 与 `dense` 的 hit 完全相同（0.941），
但 MRR 差 5.6pp（0.849 vs 0.905）。同样捞到正确文档，分数融合把它排得更靠后。
生产只把 top-3 喂给 LLM，排序质量直接决定边界上的文档会不会掉出去——
**这比 hit 更能反映真实体验，而只看 hit 会得出「两者打平」的错误印象。**

**② 等权时，两种融合方式捞到的文档完全相同。**
`wrrf50` 与 `sfuse50` 的逐个命中完全一致（不一致对 0:0），只有 MRR 不同（0.788 vs 0.807）。
说明等权融合下，RRF 与分数融合的差别**只在排序、不在召回**；
要看出召回差异，必须给稠密通道更高权重。

**③ 重排会在精确匹配题上掉分。**
`hybrid+rerank` 是唯一在 exact_match 上没拿满分的臂（0.950）。
交叉编码器看的是「问题与段落的语义匹配度」，而「X1 有几个 USB 口」的答案取决于
「X1 而不是 X1 Pro」这种**字面区分**——重排模型对此不敏感，它更愿意把讲 USB 的段落往前排。

## 3. 显著性检验：哪些差距不能说

84 道有答案题，**1 题 = 1.19pp**。McNemar 精确检验只统计不一致对：

| 比较 | Δ | 不一致对 (A胜:B胜) | p 值 | 判读 |
|---|---|---|---|---|
| sparse → dense | +15.48pp | 0 : 13 | **0.0002** | ✅ 显著 |
| dense → hybrid | −5.95pp | 6 : 1 | 0.1250 | 噪声内 |
| hybrid → rerank | +3.57pp | 1 : 4 | 0.3750 | 噪声内 |
| wrrf50 → sfuse50 | 0.00pp | 0 : 0 | 1.0000 | 命中集完全相同 |
| wrrf70 → sfuse70 | +5.95pp | 0 : 5 | 0.0625 | 差一题到显著 |
| wrrf85 → sfuse85 | +3.57pp | 0 : 3 | 0.2500 | 噪声内 |
| dense → sfuse70 | 0.00pp | 1 : 1 | 1.0000 | 打平 |
| dense → sfuse85 | +1.19pp | 0 : 1 | 1.0000 | 噪声内 |

`wrrf70 → sfuse70` 是 0:5，p = 0.0625——**离显著只差一道题**（6:0 时 p = 0.031）。
三档权重合计 8:0，方向高度一致。但"差一点"就是没到，不能写成"已证明"。

### 需要多少题

达到 p < 0.05 需要 **6 个同向不一致对**。按各组不一致率反推：

| 要检测的效应 | 不一致率 | 需要题量（约） |
|---|---|---|
| 15pp（通道级） | 13/84 ≈ 15% | **40 题** ← 当前够 |
| 6pp（融合方式） | 5/84 ≈ 6% | **100 题** |
| 3.6pp（是否重排） | 5/84 ≈ 6% | **100 题** |
| 1.2pp（参数微调） | 1/84 ≈ 1.2% | **500 题** |

**评测集的规模必须匹配要检测的效应量。** 现在 84 题够判断「用不用稠密通道」，
不够判断「用哪种融合」与「要不要重排」。再补到 150 题左右，后两类才有定论。

## 4. 一个被推翻的假设

补精确匹配题时，我预期**稀疏通道会在这一类上反超稠密**——理由听起来很硬：
「X1」是精确 token，BM25 对 token 匹配是天然强项，而稠密通道对型号这种无语义字符串
应该不敏感。

**结果相反：sparse 0.800，dense 1.000。**

原因是我把 BM25 的失效方式想反了。BM25 不是「匹配不到 X1」，而是
**「X1」也是「X1 Pro」的子串**——它给 X1 Pro 的分数同样高，甚至更高
（那篇文档更长、字段更全、token 更多）。20 道题里 sparse 错了 4 道，全是这类撞车。

而稠密通道编码的是整句语义：「X1 有几个 USB 接口」与「X1 的接口配置：4 个 USB 3.0」
在语义空间里更近，「X1 Pro 的 6 个 USB」离得更远。型号差异被语境吸收了。

教训不是「dense 更好」，而是：**对检索机制的先验判断经常是错的，尤其当它「听起来很合理」的时候。**

## 5. 建议

1. **不改生产配置**。`hybrid + rerank`（0.917）与 `dense`（0.941）的差异 p = 0.125，
   没有证据支持改动。生产配置的价值不只是分数——它保留了稀疏通道对**新出现的专有名词、
   编号、错误码**的兜底能力，而那些词还没有向量语义可言。
2. **如果要动，优先动融合而不是动通道**。8:0 的方向证据说明 RRF 的等权假设有问题：
   它把两路的「共同认可」当作可信信号，而当弱通道头部本身就是错的时，这个假设反转成负信号。
   换 `min-max` 分数融合 + dense 权重 0.7~0.85 是低风险改动（只改融合函数，不动索引），
   但要先补到 100 题以上再验证。
3. **重排值得重新评估是否保留**。`hybrid+rerank` 0.917 vs `hybrid` 0.881，p = 0.375 不显著；
   而重排在 CPU 上让每题多花 1~5 秒。**这是当前性价比最可疑的一环**——
   一个不显著的正向收益，换来可感知的延迟。

## 6. 边界

- **文档级指标**：不回答「拼进 prompt 的 3 条 chunk 里有几条有用」。语料每篇 100–400 字，
  `CHUNK_SIZE=512` 下多数只切出 1 块，chunk 级评测现在做不出来。要做，先把语料写成真正的长文档。
- **exact_match 类集中在同一产品**：20 道题都在问「智星 X1」，语料只有 6 篇产品文档。
  真实知识库的产品线更宽、干扰更多，本类的结论偏乐观。
- **口语化题是刻意构造的**：20 道题特意不与原文共用关键词以放大通道差异，
  其权重高于真实流量占比（真实流量里这类问题占比不明）。
- **语料仍是合成的**：78 篇里有 72 篇是制度文档，6 篇产品文档也是按真实问法反推编写的，
  不是真实产品手册。
- **dense 走 Ollama `bge-m3:latest`**（与生产 `EMBEDDING_MODEL_NAME` 同源），
  但生产是 Milvus 索引 + 分块检索，本脚本是 numpy 全量余弦 + 整篇文档。检索算子差异未验证。
- **统计口径**：McNemar 只看 hit 的二值结果，对 MRR 差异不敏感。
  §2 提到的 MRR 分家（sfuse70 vs dense）没有对应检验，只能作为观察。
