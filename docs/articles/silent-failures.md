# 三个静默失败

> 一个能跑通的 RAG demo 和一套能交给别人用的系统之间，差的不是检索精度，
> 而是**这个系统出错时你能不能知道**。本文只讲三件事：删除、报错、断连。
> 每一节都说清「不做会怎样」、代码里怎么做的、怎么自己验。
>
> 文中所有数字与路径都可在仓库里核对，命令见 §6。

## 0. 引子：静默失败长什么样

大多数 RAG demo 是这么长出来的：接一个向量库，塞几个文件，问一句，出来一段通顺的话。
演示的时候永远是对的——因为演示只走「正常路径」。

真实使用最先撞上的不是「回答不准」，而是三种**看起来一切正常**的故障：

| 现象 | 用户看到的 | 实际发生的 |
|---|---|---|
| 删掉的文档还能被检索命中 | 文档列表里没了 | 向量/缓存里还留着，检索照样召回，模型照样引用 |
| 报错了但没人去修 | 日志里一行 `ERROR` | 可恢复的抖动和代码缺陷混在一起，信息在写下那一行时就丢了 |
| 生成到一半切网 | 半截答案 | 生成随连接一起被取消，一次完整的 LLM 调用白烧 |

它们的共同点是**不抛异常、不告警、不自曝**。系统不会告诉你「我删了一半」，
只会安静地保留一个看起来正常的界面。这个项目的大部分工程量，花在把这三种沉默变成可判定的信号上。

## 1. 删除：「删干净」是一个顺序问题，不是一个 API 调用

### 1.1 一次删除要动四处

一份文档在系统里至少存在于四个地方：

1. **PostgreSQL**：文档行（用户能看见、能重试的那条记录）
2. **Milvus**：切片向量（决定「还能不能被检索命中」）
3. **MinIO**：原始文件（决定「还能不能被下载」）
4. **Redis**：语义缓存条目（决定「旧答案会不会被回放」）

只删第 1 处，是最常见的写法，也是最坏的写法：用户以为删了，检索仍然命中，
模型会一本正经地引用一份「已经不存在」的文档。

### 1.2 顺序为什么重要

`backend/src/services/document_tasks.py` 里删除阶段的顺序是**向量 → DB 行 → 原文件**，
而不是直觉上的「先删文件」。代码注释写得很直白：

```
- 先删向量：失败则文档原样保留，用户重试即可，不会出现
  「文件已删、记录还在、内容还能被检索命中」的半删除态（旧顺序先删文件，正是这个坑）；
- 再删 DB 行：失败则文档仍在列表但已搜不到，重试删除即可修复；
- 最后删文件且 best-effort：文件残留只是存储占用，不影响删除语义。
```

这三句话其实是一条**失败传播方向**的设计：每一步失败时，系统停在一个
「用户能理解、能重试」的状态上，而不是停在一个「看起来删了其实没删」的状态上。

第 3 步（原文件）故意做成 best-effort，失败只记 `RECOVERABLE`：

```
message="文档记录与向量已删除，仅原文件清理失败（对象存储残留，不影响检索）"
```

因为对象残留的后果是**存储占用**，不是**语义错误**。把这两者记成同一级别，
运维就无法区分「该清理磁盘」和「该修删除链路」。

### 1.3 `phase`：失败日志必须能指出卡在哪一步

删除的顶层 `except` 不是一句「删除失败」，而是带上阶段：

```python
phase = "vectors"          # → "database" → "object" → "wiki_cascade"
...
log_exception(logger, e, action="document.delete.background",
              message=f"文档删除失败（阶段: {phase}）",
              doc_id=doc_id, phase=phase)
```

前端拿到的文案也带阶段（`删除失败（database），请稍后重试`）。这不是为了好看：
卡在 `vectors` 要重试，卡在 `database` 要查约束，卡在 `object` 只需清残留，
卡在 `wiki_cascade` 说明文档本身已经删干净、只是百科页还在引用它。
**同一条「删除失败」，四种处置方式**——没有 `phase`，这四种就混成一种。

### 1.4 对账：不相信自己，只相信比对

即使顺序对了，也会有漏：进程被杀、Redis 抖动、上一次版本遗留的数据。
所以这个项目里有一个**只读**的三方对账工具 `backend/src/services/consistency_audit.py`，
用 DB 当唯一事实来源，比对三类存储：

- **Milvus ↔ DB**：向量指向已删文档 / 文档下架仍有向量 / 已发布却检索不到 / `kb_id` 为空或指向已删库
- **MinIO ↔ DB**：无主文件 / DB 引用但对象丢失
- **Redis ↔ DB**：缓存引用已删文档、所属库已删、过了 TTL 还在、索引指向不存在的 key

设计上刻意保守：

- **只报告，不自动删**。孤儿向量和孤儿对象的删除不可逆，先让人看到再决定。
- **每侧独立采集**，单侧连不上不影响其它侧，但整体退出码置 2。
- 退出码三态：`0` 干净、`1` 发现差异、`2` 巡检本身出错（连不上/查询失败）。
  **`2` 必须当故障处理**——它意味着这次巡检没看到全貌，不能当成「没问题」。

12 种问题类型（`KIND_LABELS`）各自有稳定 `kind`，nightly 任务按 `kind` 做告警与趋势对比，
而不是解析一段人话日志。

### 1.5 一个真实被它抓到的缺陷

写过一份「残留索引」的修复（仓库里记为 C12），起点就是巡检长期报 `dangling_cache_index`。
一开始记的原因是「删知识库时漏了 SREM」，实际比这宽：

> Redis 的 hash 在**删掉最后一个字段时会被整个删除**，但索引 SET 里的成员不会跟着消失。

所以**三个删除点**都有这个问题：按库失效 `invalidate_kb`、写时惰性清理 `_trim`、
命中侧 `discard`。修法是新增 `_prune_empty_scopes()`：只对「确认已删空」的 scope 做 `SREM`，
索引键 `SCARD` 为 0 时删除；**不做**「逐成员校验存在性」的兜底扫描——那会在每次失效时
对全部索引 `SMEMBERS` + 每成员一次 `EXISTS`，为了一条残留把常规路径变贵。

修完不是只跑单测，而是在真实 Redis 上造了一条 scope + 索引成员，走完整路径：
`invalidate_kb` 返回 1、scope 消失、`index:kb:<id>` 键被删、`index:all` 成员清空；
巡检复跑 `exit 0 / 6.85s / 三方一致`。

**对账工具的价值不在于它能修，而在于它能把「我以为干净了」变成一条可复现的差异。**

## 2. 报错：三级严重度，以及「异常类型优先于文案」

### 2.1 一律 `logger.error` 丢掉了什么

仓库里 `except Exception` 曾经非常多，而且各处以不同文案、不同级别记录。后果是：

- 「Redis 超时」（可恢复、重试即可）和「KeyError: 'kb_ids'」（代码缺陷、重试一万次也一样）
  **躺在同一个 error 日志里**；
- 日志里没有「该不该重试」的答案，值班的人只能靠猜；
- 更糟的是「把异常压成默认值」：打分失败 → 0 分 → 被当成「不相关」→ 系统回答
  「知识库里没有」，而实际上是重排模型挂了。**一个基础设施故障，被伪装成一个业务结论。**

### 2.2 三级 + 两条判定规则

`backend/src/utils/error_handling.py` 把异常分成三级：

| 级别 | 含义 | 日志 | 调用方可做什么 |
|---|---|---|---|
| `RECOVERABLE` | 网络抖动、超时、连接被拒、上游限流/不可用 | warning，不附堆栈（避免刷屏） | 降级或重试 |
| `REPORTABLE` | 未知业务异常、数据不一致、外部返回不可解析 | error + 堆栈 | 需要人排查 |
| `PROGRAMMING` | `TypeError` / `AttributeError` / `KeyError` / `AssertionError` … | error + 堆栈 | 修代码，重试无意义 |

判定不是靠文案关键词，而是**异常类型优先**：

```python
_PROGRAMMING_TYPES = (TypeError, AttributeError, AssertionError, IndexError,
                      KeyError, NameError, UnboundLocalError, ZeroDivisionError, ...)
_RECOVERABLE_TYPES = (TimeoutError, ConnectionError, ConnectionRefusedError,
                      ConnectionResetError, BrokenPipeError, ...)
_RECOVERABLE_MODULE_PREFIXES = ("httpx", "httpcore", "redis", "pymilvus",
                                "aiolimiter", "aiohttp", "urllib3", "sqlalchemy.exc")
```

第三方客户端的瞬时故障按**模块前缀 + 类名特征**识别，而不是 import 一堆依赖去判类型。
文案特征（`"rate limit"` / `"too many requests"`）只作为最后的弱信号，
且只在消息里出现强特征时才采信——否则任何一句带 `connection` 的业务 `ValueError` 都会被误判成可恢复。

第二条规则是**后果优先**：底层异常是可恢复的，但如果吞掉它会导致**结论错误**，就显式抬级。
最典型的就是重排失败：`_log_similarity_unavailable()` 会把「相关性无法度量、门禁退化为放行」
记成 `REPORTABLE` 而不是 warning——因为放行的代价是「可能把不相关的内容当答案给出去」，
这已经不是抖动，是正确性问题。

### 2.3 `action=` 是日志的主键

全仓 **369 处调用点 / 约 393 个 handler**，统一入口是 `log_exception(logger, exc, action=..., ...)`。
`action` 形如 `document.delete.object`、`semantic_cache.prune_index`，
是**唯一能定位到代码位置**的键（日志里可直接 `grep action=document.delete.object`）。
结构化的键值（`doc_id` / `kb_id` / `phase` / `scope`）跟着一起落，避免「日志里有堆栈但不知道是哪份文档」。

`backend/tests/test_error_handling.py` 有 **93 例**，守的主要是分类判定：
哪些类型必须判编程错误、哪些文案不能触发可恢复、抬级规则是否生效。

### 2.4 一个「告警本身也静默」的例子

Prometheus 那边出过一次典型故障（仓库记为 C10）：`postgres-exporter` 挂的
`queries.yaml` 是 v0.20 已废弃的 extend 格式，**一个采集器出错让 `/metrics` 整页 500**。
于是 PG 连接数、锁、库大小全部消失。

更麻烦的是：告警规则里当时只有两条 `up` 规则（fastapi-app、milvus），
**没有任何「数据缺席」告警**——所以它静默失败了数小时（`FailingStreak` 371）。
修复不只是改配置，还补了两条：`ScrapeTargetDown`（`up == 0`，并说明 5xx 同样记 `up=0`）、
`PostgresDatabaseDown`（`pg_up == 0`）。

教训是：**「指标消失了」和「指标正常」在大多数看板上长得一模一样。**

## 3. 断连：把「运行」从「连接」里拆出来

### 3.1 原来的形态：生成器就是响应体

流式问答最自然的写法，是让生成器直接作为 ASGI 响应体。它的代价在第一次切网时就暴露：

- 客户端断连 → `CancelledError` 从 `yield` 点抛进来 → 生成终止，只落半截答案；
- 切标签/刷新页面 = 回答作废，重问一次要再烧一次完整 LLM 调用；
- 用户点「停止」只是前端 `abort`，服务端在代理层感知断连之前仍在烧 token；
- 刷新后助手消息还没落库，界面上只剩一个孤立的问题。

### 3.2 拆开：注册表 + 带序号缓冲 + 游标

`backend/src/services/chat_run.py` 把一次问答做成一个**运行对象**：

- 生成跑在独立 `asyncio.Task` 里，事件写进带序号的 `deque` 缓冲；
- 任意客户端凭 `run_id` + 游标 `after` 重连续传，`GET /api/chat/runs/{run_id}/stream?after=N`；
- SSE 每帧都带 `id:`（就是那个 `seq`），浏览器 `Last-Event-ID` 与前端手写 `after` 都靠它；
- 可显式停止（`POST /runs/{run_id}/stop`），已生成部分保留；
- 长检索/长思考期间发 `: ping` 注释帧保活，避免代理按空闲超时掐连接。

缓冲有边界，代码里也承认边界：

> **缓冲在进程内**。进程重启即丢，跨重启恢复要等 AM-4（持久执行）；当前生产是单 uvicorn worker，
> 进程内注册表足以覆盖断线场景。
> **不做 checkpoint**。续传是「重放已产生的事件 + 继续接收」，不是从半截 Agent 步骤里恢复执行。

把边界写在模块开头，比写一堆「已支持断线恢复」的宣传有用——**读者能据此判断它适不适合自己的场景**。

### 3.3 与优雅停机是一件事的两面

续传解决「客户端断」，重启解决「服务端断」。后者如果没做，前者的努力会在发布时归零：

- 原来是 docker 默认 10s 后 `SIGKILL`，uvicorn 又无限期等待已建立的 SSE 连接
  → `lifespan.shutdown` 根本不执行 → 在途回答不落库，日志里连一句「被中断」都没有。
- 现在是三层预算：`uvicorn --timeout-graceful-shutdown 20`、`drain(grace=15)` 让回答自然写完、
  `drain(timeout=10)` 取消并保存部分答案；`stop_grace_period: 100s` 覆盖 85s 总预算。
- 实测：`SIGTERM` → **1s 退出、ExitCode=0、`Application shutdown complete`**；
  对照实验（无模型缓存）100s 被 `SIGKILL`（137），作为已知边界写进部署文档。

`backend/tests/test_chat_run.py` **35 例**，覆盖续传游标、重复订阅、停止语义、关机排空。

## 4. 三件事的共同点

把三节合起来看，会发现是同一个动作：**把一个「看起来正常」的状态，拆成「可判定的状态」**。

| 问题 | 判定信号 |
|---|---|
| 删干净了吗 | 三方对账的 `exit 0/1/2` + 12 种 `kind` |
| 这次失败该重试还是该修 | 三级严重度 + `action` + `phase` |
| 断连后能不能要回来 | `run_id` + `after` 游标 + 终态集合 |

它们都不是「加一个功能」，而是**给已有的路径补上判据**。这也解释了为什么这类工作的投入产出比
在演示阶段看不出来——它只在出错的时候兑现。

## 5. 代价（这一节必须写）

「可审计」不是免费的。同一套东西的账单：

- **部署重**：默认 7 容器（含监控 11 个），后端镜像 2.86GB，模型另需 5.6GB，标称最低 8GB 内存；
- **必须本机 Ollama**：默认完全离线是卖点，也是门槛——没有 GPU 的机器上重排会慢到 2.4s/题；
- **显存硬约束**：4GB 上限下 3B 直答与 4B 深度思考互斥，所有辅助任务必须走小模型；
- **能力仍有短板**：真实文档 24 题上，细节型覆盖率 0.792、概览型 0.598
  （「监控哪些指标、有哪些告警」会只给出一张表的三行，见 `docs/benchmarks/stage-probe-2026-11-03.md`）；
- **没有真实用户**：生产库 0 文档 / 3 用户 / 107 条 trace，所有评测都是我自己构造的问题。

一句话：这套工程化深度是**为「可判定」付的钱**。如果只是自己问几个 PDF，
它大概率是过度设计——那时候更该做的是一个轻壳，而不是这一套。

## 6. 自己验一遍

```bash
cd backend

# 1) 删除链路与对账：13 + 29 例
uv run pytest tests/test_consistency_delete_chain.py tests/test_consistency_audit.py -q

# 2) 异常分级：93 例
uv run pytest tests/test_error_handling.py -q

# 3) 断连续传与关机排空：35 例
uv run pytest tests/test_chat_run.py -q

# 4) 真跑一次三方对账（只读，退出码 0/1/2）
docker exec backend-prod python scripts/consistency_audit.py
```

期望输出形如：

```
一致性巡检 2026-11-03T04:01:46Z  用时 6.85s
DB 基线：文档 0（已发布 0） / 知识库 1 / Wiki 页 0 / 引用对象 0
[milvus] 扫描 0   ✓ 未发现差异
[minio]  扫描 0   ✓ 未发现差异
[redis]  扫描 0   ✓ 未发现差异
结论：三方一致，退出码 0
```

## 7. 本项目明确不做的

- **多租户 / 组织层级 / SSO / RBAC**：现有 `owner` 级隔离够单组织内网使用，加租户层是另一个量级的改造；
- **真 HA（多副本 / PG 主从 / 故障转移）**：9 处进程内状态需外置，单机部署没有第二台机器接管；
- **桌面端 / 免登录单用户版**：需要第二套存储抽象，是重写而非优化；
- **企业级压测与 SLA**：没有用户拿它做采购依据，「企业级」一词在三条门槛（容量实测 / ≥50 题标注集 /
  恢复演练）达标前保持冻结。

不做的理由不是「做不到」，而是**没有验收压力时做了也没人用**——这一条比技术选型更影响排期。
