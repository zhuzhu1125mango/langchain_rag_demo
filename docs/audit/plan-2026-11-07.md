### 索引验收：默认计划仍是 Seq Scan，这是对的

迁移后 `EXPLAIN` 没变成 Index Scan：

```
Limit -> Sort (Sort Key: updated_at DESC, quicksort 29kB)
      -> Seq Scan on sessions (rows=63, Rows Removed by Filter: 9)
```

原因不是索引没生效：表只有 72 行，而该用户占其中 63 行（87%），
规划器算下来「顺序扫一遍再排」比「走索引再回表」便宜。这就是它该做的选择。

把两条更"笨"的路径关掉，能看到索引本身**提供了排序顺序**（计划里没有 Sort 节点，
而且只读 50 行就停，不是读完 63 行再截断）：

```
SET enable_seqscan=off; SET enable_bitmapscan=off;

Limit (rows=50)
  -> Index Scan using ix_sessions_user_id_updated_at on sessions (rows=50)
```

结论：索引可用、确实消除了排序；等单用户会话涨到几百上千条，规划器会自己切过去。
**不**为此调 `enable_*` 参数去"让 EXPLAIN 好看"。

### 顺带修掉的三个环境坑（否则这个脚本根本跑不起来）

1. **dev 的 MinIO 凭据有两套**：`.env.dev` 里给 minio 容器的是 `MINIO_ROOT_*`，给后端的是
   `MINIO_ACCESS_KEY/SECRET_KEY`，两者长度都不一样（5/11 vs 14/14）。表现是后端能连上
   9000 端口却拿到 `InvalidAccessKeyId`，`/health/ready` 503、上传删除全挂。
   已在 `docker-compose.dev.yml` 把后端凭据显式绑定到 `${MINIO_ROOT_USER}`。
2. **dev 的 NLTK 语料在容器里权限不可读**：nltk 3.9+ 的 `pathsec.ENFORCE` 拒绝读取
   「组/他人可写」的数据目录，Windows 挂进来的 `./backend/data` 在容器里是 777，于是
   `stopwords` 加载失败 → BM25 稀疏向量缺失 → `DataNotMatchException: Insert missed an
   field sparse_embedding` → **文档处理直接 failed**。已把语料固化到镜像内
   `/opt/nltk_data`（`chmod go-w`），并把 `.dockerignore` 的 `data/**` 放行 `data/nltk_data`。
3. **探针输出混进 logger 行**：容器内 python 的启动日志会走 stdout，JSON 前面多了几行，
   `json.load` 报 `Extra data`。用 `| tail -1` 取最后一行解决。

### 演练抓到的真实缺陷（已修）

**重排整批失败 → 上下文被清空 → 用户看到「知识库里没有相关内容」。**

链路：`KBReranker.rerank` 打分失败 → 回退 RRF，`rerank_score` 变成 RRF 分（≈0.016）
→ `RetrievalMixin._calculate_relevance` 只判断「reranker 是否已加载」，拿 0.016 与
`KB_RELEVANCE_SCORE_THRESHOLD` 比 → 全部判为不相关 → `kb_stage` 里 `state.docs = []`
→ 答案变成「没有找到相关内容」。日志分级是对的（reportable），用户侧却是「内容缺失」，
正好撞在这条服务的核心主张上。

修法：回退时在结果上打 `rerank_fallback=True`，`vector_store` 透传到 Document.metadata，
相关性门禁看到这个标记就跳过 rerank 分（改走语义相似度兜底，测不出时按既有约定 fail-open）。
对照测试保证「真正打过分的低分候选仍会被门禁拦下」，没有把门禁一起废掉。

### 六次「假通过」与两个判据错误

| 现象 | 根因 | 怎么发现的 |
|---|---|---|
| B 步三次问答全 0 退出、断言找不到 rerank 日志 | 只改 `KB_RERANK_MODEL`，provider 仍是 `sentence_transformers` → 失败发生在**加载**阶段，进程置 `_model_failed` 后永久 RRF，打分路径一次都没进 | 把真实失败日志打出来才看到 `load_cross_encoder` |
| B 步候选 0 条、注入等于没做 | 复用了旧知识库：PG `chunks_count>0`、Milvus 里 0 条向量 | 基线只看退出码；改成基线必须 **sources>0** |
| A 步之后 B 步候选变 0 | 上传后没 flush 就 `docker stop` Milvus，growing segment 未落盘 | 加了 flush，并在 A 恢复后断言仍有来源 |
| 「日志明明写了，断言说没有」 | `set -o pipefail` + `docker logs \| grep -q`：grep 命中即退出 → docker 收 SIGPIPE → 管道返回 141 | 用 `grep -c` 读完整个流 |
| 三次问答都报「伪装成没有内容」 | 用答案文案（`没有找到`）当判据，而提示词本身就要求模型这么说 | 改判 `sources` 条数 |

另外两条教训：**不能编辑正在运行的 bash 脚本**（bash 边读边执行，改文件会让它读到错位内容，

上会让 Milvus 的 etcd 租约到期、进程自行退出，注入 A 改用 `stop/start`。

## 结项后复查（2026-11-09 下午）：稀疏通道长期空转

追查「泛问命中率低」时发现的**更前置的问题**，比原命题严重。

### 证据链（全部为实测，命令见下）

1. 泛问「这些文档是关于什么的？」→ 候选 3 条、rerank 分 0.027/0/0、均分 0.009 → 判不相关 → `kb_miss`。
2. 同一时刻日志里有 `action=milvus.search.sparse` 的失败：`Invalid sparse row: negative value`。
3. 查持久化词表 `bm25_documents.json`：`corpus_size=5`，`idf_word` 只有 59 个词，

4. 查 Milvus 里已入库的切片：取 5 条，**4 条稀疏向量非零项为 0**，1 条只有 1 项。

### 结论

- 稀疏通道从 11-07 起**没有信号**：词表被 5 条演练文本拟合并冻结（`_ensure_bm25_fitted`
  「词表就绪不再 refit」），真实语料的词对它全部不可见；已入库的稀疏向量也几乎是空的。
- 因此「混合检索」实际是 **dense 单通道**，且无人知晓（失败被记为 `recoverable`，
  查询向量为空时更是完全静默）。
- `docs/benchmarks/channel-ab-2026-11-02.md` 里 `hybrid+rerank` / `dense+rerank` / `并集+rerank`
  三行数字**完全相同**（0.922/0.892/0.922）——这个「相同」当时没人追问，现在有了解释。
  该 A/B 的执行路径文档没写清（**未测**），所以只能说**结论需要重跑**，不能说它一定错。

### 已修（2026-11-09，commit 见下）

1. `_convert_sparse_embeddings` **截断负权重**：Milvus 稀疏 IP 要求分量 ≥ 0，而 BM25 的 IDF
   在小语料上天然出负数 → 一个高频词就能让**整条**查询被拒。截断语义是「该词不参与打分」。
2. `search_sparse` 对**空查询向量**显式判空：`[{}]` 是 truthy，原逻辑拦不住，
   空行照发，混合检索静默降级。现在返回空 + 记一条 `reportable`（含 `vocab_size`，只报一次）。
3. 新增 `tests/test_sparse_query_guards.py` 7 例（负值截断、全负置空、正常值不变、
   空向量不发请求、只报一次）。

### 低置信兜底（2026-11-10 夜）：第三种被数据否掉的修法

提案是「重排 top1 < 0.15 时不硬答」。查证发现线上早有这道判定
（`KB_RELEVANCE_SCORE_THRESHOLD`，默认 0.3），所以改动等价于「把数字从 0.3 改成 0.15」。
用两份探针报告离线扫阈值，结论是**不该改**：

| 阈值 | 拒答 | 误拒（能答却被拒） | 漏拒（该拒却放行） |
|---|---|---|---|
| 0.15 | 2 | 1 | 3 |
| 0.30（现） | 3 | 2 | 3 |
| 0.90 | 13 | 10 | 1 |

- 真正的 4 道失败 top1 是 **0.705 / 0.775 / 0.970**，任何阈值都拦不住；
- 被误杀的「熔断触发的时间和条件」top1 = **0.019** 却覆盖率 1.00 —— 三道片段全部命中；
- 零误拒的阈值只有 0.00（等于关掉）。

机制层面：重排分测的是「问题与片段像不像」，不是「片段里有没有答案」。换相对判据
（top1−top2、top1/top2）同样重叠，两类题在「平坦/陡峭、高/低」四个角落都出现。

落地改为**拒答留痕**：`pipeline.kb.relevance_gate_suppressed`（REPORTABLE），

此前这条路完全静默 —— 用户看到「知识库里没有」，运维侧查不到任何记录。

### 折叠 + 邻块回填（2026-11-11 傍晚）：互补，成本可忽略

上一轮看到折叠后回填收益从 +4.1pp 升到 +12.5pp，本轮验证是不是同一批事实点被数了两遍。
结论是**互补**（`analyze_fold_expand.py`，生产 606 块）：

| 配置 | 概览 | 细节 | 概览字符 | 块数 |
|---|---|---|---|---|
| 不折叠 / 不回填 | 0.556 | 0.792 | 732 | 3.0 |
| 不折叠 / 回填 | 0.597 | 0.833 | 1942 | 7.9 |
| 折叠 / 不回填 | 0.597 | 0.792 | 793 | 3.0 |
| **折叠 / 回填** | **0.681** | 0.833 | 2028 | 8.0 |

决定性的一行是「监控哪些指标、有哪些告警」：回填在不折叠时 **0.00 → 0.00**，
折叠后 **0.50 → 1.00**。不折叠时 3 个名额全是指标表行，邻块自然还是指标表行，补不到告警表；
折叠把名额换成「指标 + 告警」之后，回填才补到告警表其余行与处置速查。
另外三题的回填增量在两种配置下完全一致，说明回填本身稳定、不依赖候选怎么选。

预算拐点：1200 字符 → 0.639（+8.3pp，多 350 字符）；2000 字符 → 0.681（+12.5pp，多 968 字符）。
同一预算下折叠版永远优于不折叠版，且只用 3.8 块就能到 0.597。
