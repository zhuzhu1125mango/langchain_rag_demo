## 批 A：会话列表（P0-1）

**为什么第一**：这是 8 项里唯一影响真实使用的——超过 100 条会话的用户直接看不到第 101 条，
且筛选后只显示前 100 条、没有任何提示。其余 7 项都是"证据"或"债"。

**顺序（不可颠倒）**：

1. `#25` 写迁移 → `#26` 改前端（两者可并行开发，但**部署时必须先迁移**）；
2. `#27` 部署：备份 → 打回滚标签 → `alembic upgrade head` → build → `up -d backend frontend`
   → **显式 `docker ps` 确认两个容器都 Up**（§2.2.1a 记过 frontend 停在 `Created` 的坑）；
3. 验收：`EXPLAIN` 从 `Seq Scan` 变 `Index Scan`；120 条会话能翻到最后一页；筛选切换重置。

**已知坑（写进任务说明，别现场踩）**：

- **迁移里不能用 `CREATE INDEX CONCURRENTLY`**——alembic 默认在事务里跑，PG 会报
  "cannot run inside a transaction block"。生产 4 条数据，普通 `CREATE INDEX` 毫秒完成；
  将来数据量大再改 `with op.get_context().autocommit_block():`。
- 前端分页不能只改 `useSessions`：`queryKey` 要含筛选条件与页码，否则切筛选后沿用旧页；
  批量删除/导出要明确作用域（当前选中 vs 全部筛选结果），不能只作用于已加载的一页。

## 批 B：删除链证据（P0-2）

**为什么第二**：`#28` 与已有 4 个演练脚本同构，模式已经验证过（隔离实例 + 自动清理），风险低；
而它是项目第一卖点"删得干净"目前唯一缺的端到端证据。

**关键设计（失败过一次的点，别重犯）**：

- Milvus 残留判定**必须用 `count(*)`**，不能用 `num_entities`——后者含软删除标记，
  会把"已逻辑删除"误判成"仍有残留"（或相反）；
- 上传依赖 Ollama 做 embedding，脚本要先探测；不可用时**明确报"跳过，原因…"**，
  绝不静默成功（这是这个项目一直在防的形态）；
- 自建自删，`trap` 里清理，失败也要清。

**环境限制**：生产上建库/上传属于写操作，本会话被安全策略拦过。
建议在**开发栈**跑；若要验生产，需 owner 授权或手工执行一次。

## 批 C：故障与可观测（P1）

**为什么第三**：成本最高，且其中 `#31` 需要先决定一个策略问题（见下）。

1. `#29` `fault_drill.sh`：注入 Milvus 不可达 / 打分异常 / 代码 bug 三类，
   核心判据是**"分数为 0"与"打分失败"必须可区分**。用 `docker pause` 注入，
   **只能在开发栈跑**（生产 pause 会中断正在用的问答）。
2. `#30` `/health/e2e`：真实问一句，补上"容器全绿但 Ollama 挂了"的盲区。保留 `/health/ready` 不动。
3. `#31` 接夜间：**先回答一个策略问题**——GitHub 托管 runner 起不了 11 容器 + 5.6GB 模型。
   两条路：
   - 自托管 runner（要机器）；
   - 明确不接 CI，改为本地/服务器上的定时脚本，**并在文档里写清**。
   不允许"看起来接了、其实永远 skip"的绿灯——那比没有更糟。
