**顺序（不可颠倒）**：

2. `#27` 部署：备份 → 打回滚标签 → `alembic upgrade head` → build → `up -d backend frontend`
   → **显式 `docker ps` 确认两个容器都 Up**（§2.2.1a 记过 frontend 停在 `Created` 的坑）；
3. 验收：`EXPLAIN` 从 `Seq Scan` 变 `Index Scan`；120 条会话能翻到最后一页；筛选切换重置。

**已知坑（写进任务说明，别现场踩）**：

- **迁移里不能用 `CREATE INDEX CONCURRENTLY`**——alembic 默认在事务里跑，PG 会报
  "cannot run inside a transaction block"。生产 4 条数据，普通 `CREATE INDEX` 毫秒完成；
  将来数据量大再改 `with op.get_context().autocommit_block():`。
- 前端分页不能只改 `useSessions`：`queryKey` 要含筛选条件与页码，否则切筛选后沿用旧页；
  批量删除/导出要明确作用域（当前选中 vs 全部筛选结果），不能只作用于已加载的一页。

### 索引验收：默认计划仍是 Seq Scan，这是对的

迁移后 `EXPLAIN` 没变成 Index Scan：

```
Limit -> Sort (Sort Key: updated_at DESC, quicksort 29kB)
      -> Seq Scan on sessions (rows=63, Rows Removed by Filter: 9)
```

原因不是索引没生效：表只有 72 行，而该用户占其中 63 行（87%），
规划器算下来「顺序扫一遍再排」比「走索引再回表」便宜。这就是它该做的选择。

把两条更"笨"的路径关掉，能看到索引本身**提供了排序顺序**（计划里没有 Sort 节点，
而且只读 50 行就停，不是读完 63 行再截断）：

```
SET enable_seqscan=off; SET enable_bitmapscan=off;

Limit (rows=50)
  -> Index Scan using ix_sessions_user_id_updated_at on sessions (rows=50)
```

结论：索引可用、确实消除了排序；等单用户会话涨到几百上千条，规划器会自己切过去。
**不**为此调 `enable_*` 参数去"让 EXPLAIN 好看"。

  但响应体是 `index.html`——健康路由注册在根路径，nginx 只代理 `/api/`，其余都落到 SPA 的

  也就是说**从站点侧目前根本探不到真实健康**；容器 healthy 来自容器内
  `127.0.0.1:8000`，那个才是真的。要修需在 nginx 加一条显式 `location = /health/ready`
  或把健康路由也挂到 `/api` 下。已并入 #34 的文档补充项。

### 一次干净运行的结果

| 时点 | documents | Milvus(document) | Milvus(kb) | MinIO 对象 | Redis scope |
|---|---|---|---|---|---|
| 删除前（基线） | 1 | 5 | 5 | 1 | 1 |
| 删除后 | 0 | 0 | 0 | 0 | 0 |

`chunks=5`：txt 被切成 5 片，对应 Milvus 5 条向量 —— 说明「基线的 5 不是凭空来的」，
删除后归零才有意义。没有基线那一步，断言「=0」在什么都没传的情况下也成立。

### 断言不是恒真的（自测）

| 注入 | 结果 |
|---|---|
| `INJECT_RESIDUAL=redis` | exit 1，两处 FAIL：scope key 1、反向索引 1 |
| `INJECT_RESIDUAL=minio` | exit 1，一处 FAIL：对象数 1 |
| 不注入 | exit 0，七项断言全 ok |

注入物在退出前自动清掉，重复运行不受污染。

### 退出码语义

- `0` 四处干净；
- `1` 有残留（打印 doc/kb/user id 与四处定位表达式）；
- `3` **没跑**（开发栈没起、Ollama 缺模型、注册关闭）。跳过不当成功。

### 顺带修掉的三个环境坑（否则这个脚本根本跑不起来）

1. **dev 的 MinIO 凭据有两套**：`.env.dev` 里给 minio 容器的是 `MINIO_ROOT_*`，给后端的是
   `MINIO_ACCESS_KEY/SECRET_KEY`，两者长度都不一样（5/11 vs 14/14）。表现是后端能连上
   9000 端口却拿到 `InvalidAccessKeyId`，`/health/ready` 503、上传删除全挂。
   已在 `docker-compose.dev.yml` 把后端凭据显式绑定到 `${MINIO_ROOT_USER}`。
2. **dev 的 NLTK 语料在容器里权限不可读**：nltk 3.9+ 的 `pathsec.ENFORCE` 拒绝读取
   「组/他人可写」的数据目录，Windows 挂进来的 `./backend/data` 在容器里是 777，于是
   `stopwords` 加载失败 → BM25 稀疏向量缺失 → `DataNotMatchException: Insert missed an
   field sparse_embedding` → **文档处理直接 failed**。已把语料固化到镜像内
   `/opt/nltk_data`（`chmod go-w`），并把 `.dockerignore` 的 `data/**` 放行 `data/nltk_data`。
3. **探针输出混进 logger 行**：容器内 python 的启动日志会走 stdout，JSON 前面多了几行，
   `json.load` 报 `Extra data`。用 `| tail -1` 取最后一行解决。

### 未测（按 #34 约定标注）

- **只跑了开发栈**：生产上建库/上传是写操作，且没有可用的登录凭据；脚本支持
  `API_BASE/ BACKEND=` 指向生产，但要 owner 明确授权后手工执行一次。
- **只验证了一个 txt、5 个切片**：不能证明「大批量删除」「PDF/OCR 文档」「Wiki 级联」
  同样干净；这三点仍未测。
- **Milvus 的 `count(*)` 是强一致读**：如果 Milvus 侧删除延迟到 compaction 之后才反映，
  断言会看到假残留。本次实测是立即归零，但没有在压力下复验。
